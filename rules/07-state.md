# 정본·경험 연속성·저장·복원

규칙판: 생존 호러 안정화판 2026-11-17. 정확한 배포 식별자는 RULESET.json. 상시 서사·묘사는 프로젝트 지침, 상황별 조회는 00-index.md. 필요한 절만 읽는다.

## STATE_AUTHORITY

**신규 생성·독립 재시험·재개의 구별:** 새 세계/다시 생성하는 테스트는 현재 실제 로드한 룰북 배포판과 확정 입력으로 CAMPAIGN_SETUP_PIPELINE을 실행하고 새 campaign/session 식별자로 독립된 정본/최초 상태를 만든다. 이전 세이브·이전 정본·요약을 기본 생성 재료로 자동 로드하지 않는다. 같은 원작을 지정한 것은 옛 세계 재개 요청이 아니다. 실제 진행 중 본부 임무/계정 제약을 임의 새 ID로 우회하지 않는다. 기존 캠페인의 재개/같은 저장본 검사는 STATE_RESUME으로 원래 정본과 상태를 보존하며, 룰북 갱신만으로 그 세계를 재생성하지 않는다. 입력이 실제로 어느 쪽인지 불명확할 때만 구별을 확인한다.
**완료 상태의 구별:** 설계 내용 완료는 04의 실제 정본/초기 상태 대조 결과다. 정확한 배포 식별·원문 전달·운영 저장/verify는 각기 실제 결과로 알린다. 내용 결함을 저장 장애로 처리하거나 로컬 요약을 verified checkpoint라고 부르지 않는다. 로컬 테스트는 미등록/미검증임을 표시하되 작성된 사실과 입력 대기를 보존한다. 실제 외부 저장 실패는 STATE_SAVE_FAILURE_CONTINUE를 따른다.

적용: 실제 정본/저장/복원. 현재 확정 진행은 작업 상태에, 영속 진행 정본은 Supabase verified history에 둔다. 신규 기본은 Supabase 비공개 정본 원문+DOCUMENT_BOUND(DB1) 누적 동적 체크포인트다. 정확한 정본 .md 원본 파일도 소유자에게 전달해 프로젝트 소스에 보관하게 한다. GitHub 세이브/미러는 생성하지 않는다. 수동 저장의 시나리오별 상세 기록·본부 통합 출격 연대기/연결 명세는 HQ_SORTIE_STORY_ARCHIVE·STATE_COMMIT의 별도 참고 기록이며 현재 상태의 경쟁 원장이나 공개 GitHub 미러가 아니다. 외부 차단 자체를 해결하는 기능이나 별도 영구 메모리를 이 문서가 만들지는 않는다.
현행 대상은 trpg-state-v2 / project ref taoaffdyssqtnjszumpq / public.gm_checkpoint_history의 verified history 및 원문 state_json이다. 이 신규 DB에는 gm_sessions 최신 미러를 만들지 않았으며 verified history가 유일한 정상 복원 정본이다. 최초 연결/실제 변경 때 공개 데이터 API가 아닌 인증된 권한 있는 Supabase 연결과 trpg_v2_commit/verify/load_version/load/list/inspect_pending의 실제 계약을 확인한다. 확인한 계약은 같은 조건에서 재사용한다.
인증된 연결을 사용하고 키를 출력하지 않는다. 일반 판정/NPC 대화에 DB를 호출하지 않는다. 필요한 값이 현재 상태에 있으면 사용한다. 저장 완료는 실제 verify+동일 version read-back 뒤에만 표시한다. 차단·검증 실패는 STATE_SAVE_FAILURE_CONTINUE로 처리하며 운영 테이블/함수/권한/외부 앱을 임의 변경하지 않는다.

원격 기여는 E 체험으로 인정하지 않으며 모든 참가 PC가 각 E를 현장에서 직접 체험한다. 세계 E의 발생/해결과 PC별 지식·체험·수락은 별개로 기록한다. E 위기는 반드시 발생하도록 미리 독립 인과를 준비하지만 PC의 이동/수락·판정·부상/광기·사망을 대본으로 확정하지 않는다. 죽거나 제압된 개체의 손실·피해 0·국지 안전은 동적 상태에서 보존한다. 남은 E가 있는 최종 국면은 설계 실패다. 새 서버 컬럼·추가 정본 절·새 영구 저장소는 만들지 않는다.

**정본 생성/전달/등록:** 같은 전체 UTF-8 원문으로 키퍼용 비공개 `PRIVATE_CANON_<campaign_id>_r<revision>.md` 원본 파일을 소유자에게 전달하고, Supabase 비공개 `trpg_private.gm_canon_documents`에 저장한다. 소유자는 원래 파일을 프로젝트 소스로 보관한다. 업로드를 기다리느라 DB 저장을 미루지 않는다. 공개 GitHub/게임 지문/HUD에 비공개 원문을 노출하지 않는다. 원문 SHA-256과 실제 저장된 동일 판본 전체 read-back을 대조해야 verified다. 파일 전달·DB 저장·read-back 검증·프로젝트 업로드는 각각의 실제 결과로 구별하며 하나의 성공을 다른 성공으로 꾸미지 않는다. 정본 검증 후 setup_bootstrap 체크포인트는 STATE_COMMIT의 commit→verify→동일버전 read-back으로 잇는다.

**판본·누적 변화:** 현재 적용 규칙판과 정본 원문 판본/SHA는 STATE_IDENTITY로 구별하고, 정본 참조는 STATE_CANON_SAVE_BINDING으로 체크포인트와 일치시킨다. 최초 사실은 정본, 이후 PC/NPC/적의 실제 반응·위치/소유·생사·사건 처리와 경험은 누적 world_delta/STATE_WORKING_CONTEXT다. 최초 정본으로 최신 상태를 덮거나 이미 처리한 E/S/난수를 재생하지 않는다. 중요한 정본 오류는 근거·변경 범위를 명시한 새 판본으로만 보완하며 구판 verified 원문/해시·손실/안전·구판 시간표/종결을 재작성하지 않는다. 재개는 신규 생성이 아니다. 실제 저장 실패는 STATE_SAVE_FAILURE_CONTINUE/STATE_RECOVERY로 처리한다.

정본 초안은 CAMPAIGN_SETUP_PIPELINE의 생성 완료 대조 **이전**에 작성한다. 필수10절 제목·규칙 요약만 채우지 않고 04의 준비 결과인 실제 개체·장소·수량/소유·사건 전후 상태를 수납한다. COMPATIBILITY_GATE를 통과한 같은 원문을 전달/등록한다. 공개본에 비밀을 옮기거나 검사 뒤 별도로 세계를 다시 지어 서로 다른 원문/첫 상태를 만들지 않는다. 정본에는 실제 준비 사실·개체별 조건/값과 담당 룰 ref를 담고 공통 판정·저장 금지문 전문을 반복 복사하지 않는다. 고유 발언/인과·행동 조건은 줄이기 위해 버리지 않는다. 작성용 `templates/PRIVATE_CANON_TEMPLATE.md`는 이10절의 빈 폼이며 실제 캠페인 정본/세이브가 아니다. 폼의 자리표시자를 실제 사실로 채우고 원작 예상별 경로 대조와 리뉴얼 고정 사실/대체 ref를 해당 절에 담는다. 폼에 있는 예시/빈칸을 실제 사건으로 복사하지 않는다.

## PRIVATE_CANON_ACCESS_ROUTER

필요한 실제 사실 → 현재 작업 상태 → Supabase에 검증된 해당 campaign/canon/revision 비공개 정본의 절/entity → checkpoint 순서로 확인한다. 동일 판본을 이미 조회했으면 재사용한다. 프로젝트 .md는 동일 원문을 보존하는 소유자용 파일/복구 자료다. NPC는 현재 기억+해당 baseline, 단서는 현재 소유/발견+원문, 법칙/위협은 현재 발동/차단+능력, 공간은 현재 경로+지도, 시간 진행은 활성 원인 색인+관련 조건, 종결은 실제 결과+ENDING_CONDITIONS를 쓴다.
campaign_id+canon_id+revision+절/entity ID로 조회하고, 현재 확인 가능한 같은 본문이 있으면 재조회하지 않는다. 신규 생성 중의 현재 정본 초안/최초 작업 상태는 그 새 campaign/session의 작업 사실로 사용하고 미등록/미검증 상태를 구별한다. 원작명·파일명이 비슷하다는 이유로 이전 테스트나 다른 판본의 정본을 현재 초안 대신 로드하지 않는다. 룰북 절차와 실제 캠페인 사실을 구분한다. 정본의 옛 기준선에 최신 누적 변화를 적용하며 동적 값이 유실됐다고 초기값으로 채우지 않는다.
Supabase 정본 원문이 없거나 SHA/판본이 다르면 canon_source_required로 의존하는 결과만 보류한다. 장애 시 프로젝트 파일의 동일 SHA 원문을 확보해 한시적으로 활용할 수 있으나 Supabase 정본 조회 성공으로 가장하지 않는다. 필요한 사실을 일반 예시로 생성하지 않는다. 비공개 내용을 조회보고/HUD에 붙이지 않는다. 정본 읽기는 게임 시간/턴/난수/저장 행동이 아니다.

## PRIVATE_CANON_PERIODIC_REVIEW

정본의 Supabase 등록·활성 판본 교체·새 채팅 로드 시 전체 원문과 파일 해시를 한 번 확인한다. 기존 정기 재독은 Scene Turn20/40/60…에 도달한 뒤 열린 절차가 끝난 첫 안전 경계에서 수행한다. 동일 응답에서 같은 전체 원문을 이미 읽었으면 재사용한다. 여러 경계를 넘으면 현재 한 번, 다음 기준은 현재보다 큰 다음20배수다.
색인에 있는 활성 모든 절/파일의 실제 본문을 확보해 기준선+현재 누적 변화를 대조한다. 검색 발췌/잘린 원문/요약만으로 전체 완료라 하지 않는다. 기존 미저장 결과를 먼저 보존하고 사망·발견·취소를 초기화하지 않는다. 미래20턴의 사건/PC선택을 만들지 않는다.
판본·확인 범위·완료/누락·다음 기준을 현재 상태에 남긴다. 조회 실패는 미완료이며 필요한 현재 사실이 남아 있으면 플레이는 계속한다. 상태 변경/명시적 재시도/다음 정기 경계에 누락 범위를 다시 읽고 같은 장애를 매 응답 경고하지 않는다.
정본 재독20턴과 저장40턴은 별개다. 겹치면 같은 본문을 재사용한다. 재독을 위해 DB 저장/전체load를 추가하지 않으며 재독 성공을 저장 성공으로 대체하지 않는다. 이 주기는 무손실 기억의 보장이 아니다.

## STATE_CANON_SAVE_BINDING

신규 기본 DOCUMENT_BOUND(DB1)은 Supabase 비공개 정본 전문의 정확한 참조+완전한 누적 동적 상태를 결합한다. 정본 원문과 checkpoint는 같은 Supabase의 별도 저장 단위다. 현행 V2 서버 계약은 state_schema_version=TRPG_STATE_V2·save_mode=DOCUMENT_BOUND·document_bound_format=DB1이며, rules_version은 실제 사용한 룰북판을 별도로 기록한다. 버전 문자열로 삭제된 구형 상태필드나 이전 RNG 큐를 필수화하지 않는다. 새 RPC의 실제 수용/검증 계약을 확인한다. 룰북 업로드로 서버 계약이 바뀌지는 않는다.
| 구성 | 필요한 데이터 |
|---|---|
| canon_ref | campaign/canon ID·revision·filename·document_format·전체 바이트 file_sha256·필수 section_ids와 실제 PC/챕터 참조 |
| change_coverage | complete_since_revision=true; baseline_entity_ids와 changed_entity_ids의 npcs/evidence/locations/routes/drivers/threats6개 전체 집합 |
| world_delta | 같은6개 namespace별 정본 이후 누적 현재값/변경 근거. changed집합은 실제 object 키와 일치 |
| new_entities/tombstones/processed_event_ids | 신규 인물/단서/원문·사망/소모/취소/종결·실제 처리event, 현재 실행 플래그 |
| PC/진행 | session/campaign/규칙판·phase/챕터/턴·설정/시드·전원 identity/수치/자원/위치/장비·공개 사실/지도·시간·선언/판정/전투/질문 대기·약속/획득·저장주기·종료/후일담 상태 |
| 재개 문맥 | STATE_EXPERIENCE_CONTINUITY의 이야기·인물·현재 장면/미해결 상태와 원문/이벤트 참조 |
현행 V2 checkpoint payload 최상위에는 `session_id`, `campaign_id`, `rules_version`, `state_schema_version`, `save_mode`, `document_bound_format`, `checkpoint`, `canon_ref`, `change_coverage`, `world_delta`, `new_entities`, `tombstones`, `processed_event_ids`, `pcs`, `runtime`, `story_context`, `npc_contexts`, `scene_context`, `ongoing_consequences`, `critical_state_registry`, `manifest`를 둔다. 별도 JSON객체를 원문 상태에서 만들어 현재 맥락을 빠뜨리지 않는다. `checkpoint`에는 `version`·`event_id`·`attempt_id`·`parent_version`·`parent_sha256`를 두며 첫판의 parent는 명시적 null이다. `pcs`는 P1~P3 중 실제 인원만의 객체, `runtime`에는 phase·scene_turn·current_pc·pending을 포함한다. `canon_ref`에는 campaign_id·canon_id·revision·filename·document_format·file_sha256·필수10절의 section_ids를 둔다. 신규 세션에는 구형 RNG 큐가 필요 없다. 신규 canon_ref.file_sha256은 Supabase gm_canon_documents.file_sha256 및 전달한 Markdown 원본의 UTF-8 바이트 해시와 일치해야 한다. 첫 setup_bootstrap checkpoint 전에 해당 canon 원문과 read-back을 검증한다.
캠페인/챕터/최초프로필 전문·scenario_core/world_dna/canonical_map_model/world_state 같은 불변 전문은 매 전송에 중복하지 않고 정확한 정본 참조로 복원한다. 실제 신규/변경 정보는 제외하지 않는다. 마지막 저장 뒤 delta만 남기는 체인은 금지한다.
새 payload 객체를 만들되 작업 상태 자체는 삭제/축소하지 않는다. 실제 지원되는 기존 동적 namespace/runtime_flags 등에 재개 문맥을 보존할 수 있는지 계약과 read-back으로 확인한다. 필드를 거부/삭제하면 호환 실패다. 가짜 빈값이나 불변 전문을 다른 필드에 숨겨 통과시키지 않는다.
복원은 정본+누적 world_delta+new_entities+tombstones+processed_event_ids+PC/실행/재개 문맥을 결합한다. 파일 SHA/판본/coverage 누락은 canon_source_required 또는 checkpoint_canon_recovery_required로 해당 복원을 보류한다. DB1 차단을 감추려고 대용량 LEGACY_FULL을 자동 재전송하지 않는다.
기존 LEGACY_FULL 원문/해시/history는 유지한다. 명시적 해당 세션 변환 요청과 원문/정본 항목별 대조·필요한 새 판본·새 버전 verify/read-back 없이 자동 이관하지 않는다. 과거 GitHub 저장본은 삭제하지 않지만 신규 생성/자동 미러/복원 대상이 아니다. 기존 세이브의 참조는 소급 변경하지 않으며, 소유자는 기존 정본/구판 .md를 보존한다.

**최초 정본→작업 STATE→출력의 연결:** 신규 setup_bootstrap 이전에 통과할 정본 초안과 최초 작업 상태를 아래처럼 한 번 연결해 COMPATIBILITY_GATE 입력으로 사용한다. 기존 V2/DB1 JSON 범위의 사용 안내이며 서버 컬럼/새 최상위 키를 추가하지 않는다.
- `pcs[Pn]`의 identity·실제 수치/소유·위치, `scene_context`의 첫 장소/세계 기준 시점·현재 관측·열린 첫 입력은 정본의 같은 초기 사실을 읽는다. `runtime`의 phase=setup/scene_turn=0·실제 pending과 짝지으며 실제 시작 선언 뒤 기존 play_start 전이를 사용한다. 세계 G의 선행 발발, PC가 아는 것, 아직 하지 않은 이동/대피·첫 위해 관측은 서로 복제하지 않는다.
- 초기 적/주요 NPC·자원/시설의 기준은 canon_ref의 실제 baseline이다. 기존 `npc_contexts`에는 대화/관계·현재 행동에 필요한 해당 인물의 시작 맥락을 연결하고 `story_context/scene_context`에 현재 E/최종 진입 경계와 PC별 미체험/입력 대기를 잇는다. 최초 이후 달라진 실제 정보/행동만 누적 world_delta로 기록한다. 첫 world_delta가 비어 있다는 사실 자체는 정상이며 초기 개체가 정본에서 누락되어도 된다는 뜻은 아니다.
- 공개 프로필·공개 상태 요약·비공개 체크포인트·첫 지도/지문은 **동일 최초 작업 상태의 투영**이다. 따로 창작하지 않는다. 첫 위치를 ‘시작 때 결정’으로 비워 놓거나 비공개 NPC만 이미 대피/승선한 미래에 배치하지 않는다. 공개본에는 각 PC의 실제 지식만 내보낸다. 소유/위치·현재 단계·수치·장전/예비탄과 정본 판본/SHA가 다르면 내용 완료 이전에 맞춘다.
- 운영 저장은 위 기존 V2/DB1 필수 payload·정본 원문·SHA와 STATE_COMMIT을 따른다. 단순 로컬 테스트 요약은 그렇게 명시하고 운영에 그대로 넣을 세이브/검증 완료로 표시하지 않는다. 완전한 로컬 작업 상태와 비공개 원문은 보존하며, 생성 로그/시드·공개 프로필만을 최초 STATE라고 부르지 않는다. 로컬 시험/채팅 이동용 파일을 요청받으면 STATE_RESUME의 실제 전체 상태·정본·판본 묶음을 전달한다. 해당 요약 파일이 가진 사실과 표준 checkpoint를 혼동해 가짜 필드/과거 검증으로 메우지 않는다.

**본부 ON의 기존 종결 저장 계약:** 서버 변경 없이 기존 JSON에 다음 실제 값을 기록한다. OFF에는 요구하지 않는다.
- `runtime.hq.enabled=true`, `runtime.hq.mission_id`는 실제 임무 UUID, `runtime.hq.segment_key`는 해당 현지 구간과 정확히 일치시킨다. 추정 ID를 발급하지 않는다.
- `runtime.ending_state.scope`는 CAMPAIGN_TERMINAL/CHAPTER_TERMINAL/CHRONICLE_TERMINAL 중 실제 범위, `status`는 completed/failed, `finalization_event_id`는 실제 종결 event다. `returning_agent_ids`는 **실제 귀환하는 영구 요원 UUID 배열**이며 중복·미참가 ID·죽거나 SAN 0으로 행동 자격을 잃은 인물을 넣지 않는다. 전멸이면 빈 배열/failed이며 귀환/보상을 꾸미지 않는다.
- `pcs`는 실제 참가 P1~PN 객체이며 각 현재 담당 인물의 `player_id`는 연결된 영구 UUID, `alive`는 실제 생존/게임 진행 자격의 boolean이다. SAN 0도 게임 오버이므로 이 판정에서는 false로 기록하되 육체 사망과 광기 이유는 실제 HP/SAN·문맥에서 구별한다. 적법한 NPC 인계를 마친 경우 현재 인물의 새 identity/실제 상태를 잇고 이전 인물의 종료 기록은 보존한다. 연대기 종결 서버는 참가자당 정확히 하나의 player_id/alive·귀환자 alive=true·사망자 존재 시 failed·전체 completed의 전원 귀환을 요구한다.
- 최상위 `rules_version`에는 현재 적용한 최신 소스 배포 ID를 쓰고 canon_ref·SHA는 실제 정본과 일치시켜 STATE_COMMIT의 commit→verify→동일버전 read-back을 마친다. HQ의 `confirm_segment_terminal(segment_id, checkpoint_version, checkpoint_sha256, expected_revision)`에는 실제 **최신 verified** version/SHA와 최신 본부 revision을 사용한다. 필수 연결이 누락되면 기존 저장을 위조/덮지 않고 실제 계약 오류를 보고한다. 정본 등록 당시 규칙판과 현재 진행 규칙판의 차이는 STATE_IDENTITY의 갱신 이력으로 구별하며 그 차이만으로 정본을 재등록/재해시하지 않는다.

**신규 동적 저장의 의미 소유권(기존 DB1 수납):** 실제 서버의 `story_context`·`scene_context`·`ongoing_consequences`·`pcs`·`runtime`은 JSON 객체이고, `world_delta`는 기존6개 namespace다. **새 최상위 필드·테이블/RPC·정본 절·별도 진행률 장부 없이** 다음 사실을 그 담당 영역에 누적한다. 이는 E마다 의무 빈칸을 채우는 표가 아니라 실제 변화/활성 상태가 생긴 경우의 수납 계약이다.
- **일반 E/거대 G 세계 상태:** `world_delta.drivers[기존 E-ref]`는 정본 이후 실제 발생/활성·부분 대처/완전 해결·실패/미개입·차단과 남은 핵심 문제/변화 원인·근거 이벤트의 누적 현재 상태를 담당한다. `world_delta.npcs/locations/routes/threats/evidence`에는 그 결과 실제 바뀐 개체의 생사/인지·시설·출입/이동·유한 적·물품/소유만 기록한다. 거대 G 자체는 정본의 기존 참조를 유지하고 각 E가 실제 변경한 최종 대응 자원/위험만 누적한다. 단순 '현장 도착', 작은 목표·S 수락/완료나 화면 밖 전언을 E 완료로 기록하지 않는다.
- **PC별 현재 목적·정보와 E 세계 상태의 기존 저장 참조:** `story_context.main_track_by_pc`는 새 필수 스키마가 아닌 기존 체크포인트 재개 문맥이다. `world_delta.drivers`의 E/G 원인·진행·차단·세계 결산과 별개로 해당 P슬롯의 실제 선언/수락 목적, 직접 관측한 정보·위치/접근, 제안/보류/거절/완료·S/생활을 구별해 보존한다. E가 아직 남았다는 이유로 PC가 수락한 것으로 기록하지 않고 서로 다른 PC의 인지·장비/동행을 자동 복제하지 않는다. 기존 검증 세이브 비소급.
- **실제 행동권·열린 단계:** `pcs[Pn]`에 인물별 HP/SAN/Luck·중상/의식·의료품 사용/회복 제약·현금·실물명/수량/장착·구획/확장 가방·위치/확인된 지식을, `runtime`과 `scene_context`에 현재 행동권자·선택 메뉴 원래 intent/ref·열린 판정/전투/추격/광기·질문/대답 대기·미선언 이송/합류와 실제 시간 정산 경계를 보존한다. PC 교대와 저장/재개는 열린 행동의 자동 실행·재굴림·시간 증가가 아니다.
- **세계의 진행 중인 위험/구조:** `ongoing_consequences`에는 실제 화재/침수·감염/적 행동·운반/구조 등 **이미 성립한** 과정의 시작 사실/상대 경과·악화/완화/중단·관측자·관련 E/개체 ref를 보존하고, 실제 바뀐 대상은 각 `world_delta`에 반영한다. HP0 의식불명 PC는 해당 시점의 **실제 접근·이송 가능한 다른 생존 PC와 위치/퇴로·구조 진행·현장 위험**을 근거와 함께 남긴다. 구조자 전원 사망·실제 구조 불가능/일격 즉사로 이미 확정한 사망을 로드 후 의식불명으로 되돌리지 않는다. 구조자 전투 중이라는 이유만으로 불가능으로 만들거나 빈사 시계/전투 중 HP 회복을 추가하지 않는다.
- **원장과 공개 UI의 분리:** `processed_event_ids`는 실제 이미 적용한 event만 중복 없이 보존한다. `change_coverage.changed_entity_ids`의 여섯 집합과 `world_delta` 여섯 객체의 키는 **각 namespace별 정확히 일치**시킨다. 세계 개체가 변경되지 않은 PC의 목표/대화/HUD 변화만으로 가짜 드라이버 delta를 만들지 않는다. HUD는 06-play BOTTOM_HUD_CONTRACT의 고정 레이아웃으로 **현재 원장값을 투영**하며 초록/빨강 증감·경고 색상·화면 문자열 자체를 새로운 HP/물품이나 세계 사건으로 저장하지 않는다. 재개 직후 지난 턴의 색상 증감을 새 사건처럼 반복하지 않도록 `scene_context`의 마지막 실제 결과/표시 경계를 활용하되, UI 출력만을 위해 턴·이벤트·저장을 늘리지 않는다.
- **ON의 영속성 분리:** 이미 발급/승인된 본부 입단·카드 소유/영구 성장·작전평가/보상은 실제 기존 HQ/카드 원장을 우선한다. checkpoint에는 그 실행 단계/입력 대기·확인한 ref·현지 PC 스냅샷/실물 상태만 연결하고 재개로 지급·성장 적용·귀환/평가를 재실행하지 않는다. OFF에는 가상의 본부/카드 필드를 필수화하지 않는다.

## STATE_WORKING_CONTEXT

작업 상태는 실제 로드/생성한 데이터+이후 확정 변화다. 현재 문맥과 실제 지원되는 비공개 작업 공간만 사용한다. 추론을 영구 장부로 간주하거나 없는 파일/백그라운드 서버를 주장하지 않는다. 전체 보존 범위는 STATE_SCHEMA, 이야기/인물 맥락은 STATE_EXPERIENCE_CONTINUITY가 담당한다.

현재 처리에는 session/규칙판·설정/플레이 단계·관련 PC/장소·마지막 대화/열린 행동/판정·실제 다음 조건·미저장 변화만 유지한다. 준비/재개에서 실제 확보한 관련 규칙의 조건/절차/예외·정본 ref와 현재 유효한 카드 효과도 현재 확인 가능한 문맥에서 재사용한다. 축약본이 담당 원문을 대체하거나 유실된 원문을 기억한다고 주장하지 않는다. 실제 변화 때 피해/치료·물품/인계·새 합의/확인된 이해·말투/태도/관계의 이유·세계 원인/개체 상태와 의미를 즉시 갱신한다. 저장 때까지 미루거나 완료 장면의 과거 경험을 현재 요약으로 덮지 않는다.

E의 세계 발동/진행/해결·잔존 위험은 `world_delta.drivers`, PC별 실제 목적·지식/관측·제안/수락/거절·각 E 현장 직접 체험은 기존 `story_context/scene_context`의 지원되는 문맥에 구별해 잇는다. 원격 기여는 체험으로 인정하지 않는다. S/생활은 E 하위 작업과 구별하고 미발견/접촉/보류/거절/완료·NPC 독립 처리/소진과 후속 접촉의 출처를 보존한다. 현재 🎯에는 해당 PC가 실제 아는 상황·선택한 목적만 투영한다. 다른 PC의 위치·미전달 정보·수락을 자동 공유하지 않는다.

PC 교대/주요 결과에는 05-world SCENE_CONSEQUENCE_RULE의 관련 후속 접점만 확인한다. 실제 경과/변경 ref에서 영향을 받는 적·NPC·환경의 다음 조건과 도달을 갱신하고, 매 응답 전 개체의 과거/미래 행동을 다시 시뮬레이션하지 않는다. 화면 밖 독립 진행·전투/추격·20턴 정본 재독을 생략하는 캐시로 쓰지 않는다. 새 GO·핵심 비밀/적·서버 컬럼/임의 event ID·매 턴 전수조회/저장을 추가하지 않는다. 신규 도입의 실제 생활/위치·play_start와 첫 E 접촉·실제 경과/Scene Turn을 보존하고 재개 후 1턴으로 초기화하거나 사건을 재예약하지 않는다.

국지 피난/보호·공격 종료는 해당 `world_delta`/`ongoing_consequences`에 실제 성립 시점·대상/범위·유지/해제 조건과 남은 원인 ref/다음 행동·이미 지불한 이동/전환/재정비·남은 경과를 잇는다. 같은 현재 사실을 여러 독립 원장으로 복제하지 않는다. 저장/로드에서 **현재 안전을 영구 면책으로 확대하거나 종료한 공격을 다시 진행 중으로 바꾸지 않는다.** 임시/영구 여부가 기록에 없으면 실제 정본/과거 기록으로 확인하고 만료 시간·새 위협·지급/피해를 창작하지 않는다. 기존 수납 범위를 쓰며 새 최상위 필드/DB 스키마·매 턴 저장을 추가하지 않는다.

반응형 후속은 실제 확정 후 기존 지원 상태·누적 변화에 기록한다. 열린 선택의 대상 PC·관련 NPC의 실제 위치/지식·미완료 결과를 잇고 재개에서 새 무작위 사건처럼 반복하지 않는다. 실제 read-back 전 영속 성공을 주장하지 않는다. 필요한 원본/과거 경험이 없으면 관련 부분만 실제 기록으로 복구한다. 현재 미저장 진행이 남아 있으면 저장 실패를 이유로 과거 snapshot을 다시 로드하지 않는다. 구판의 확정 ref·시계·생사·소유·완료/안전/종결은 소급 재설계하지 않는다.

추적·경비·배회 전력의 현재 행동은 관련 적 ref별 실제 위치/활동권·마지막 확보 정보/흔적과 대상·진행 중 이동/수색·보호 대상/경비 이탈 한계·다음 조건/자원·중단/퇴각·유한 풀 잔여량을 기존 동적 namespace의 지원 범위에 보존한다. PC 현재 위치를 적의 마지막 확인 위치로 자동 덮지 않는다. 마지막 E의 실제 종료 상태와 최종 진입/진행은 같은 ‘완료’로 합치지 않고 해당 driver/scene 문맥에서 구별한다. 신규 공동 출발의 사전 관계/서로 아는 범위·공통 장소/일과 메인 무대 봉쇄·최종 보스의 실제 상태는 정본 baseline을 참조하고 이후 분리/이동·발견/격퇴 변화만 누적한다. PC별 처리 시각/작업·정보 전달·구조 도달 가능성과 인계 사용/현재 주체도 기존 지원 문맥에 보존하며 새 서버 필드나 baseline의 전수 복제를 요구하지 않는다. 주요 성취/거절·위해 중단 뒤에는 이미 처리한 적/위험·S·SAN 성취 보상을 다시 실행하지 않는다.

중간 치료/성취 회복은 기존 `pcs`·실물 원장·`story_context/ongoing_consequences`의 해당 ref에 실제 조건 충족·미처리/적용·대상 identity·굴림/상한 적용값·소진 event/잔여 수량을 잇는다. 준비된 기회는 지급 완료가 아니며 시도 실패의 의료품 소모도 보존한다. 저장/로드·다른 해법으로 같은 회복을 재지급하거나 다음 미지급 성취를 소진시키지 않는다. 하루 SAN 누적 손실에서 회복을 빼지 않는다. 별도 최상위 필드/DB 변경·매 턴 전수 검수는 추가하지 않는다.


## STATE_ACCESS_ROUTER

일반 응답의 기본값은 DB 조회0회다. 규칙은 담당 룰북, 현재 수치/비밀/원문/예정 사건은 작업 상태와 관련 정본을 쓴다. 현재 필요한 상태 필드/ref 또는 저장 작업과 실제 접근 사유가 있을 때만 호출한다.
허용 경계: 새 채팅/명시 로드, 필요한 상태의 실제 유실/충돌, 정상 저장의parent/commit/verify/exact read-back, 같은attempt 실패 복구, 수동 스토리 생성/복구에 필요한 지정 세이브·기록 대조, 사용자 명시 대조/목록, 최초/변경 연결 계약 확인. PC교대·대화·판정 요청/입력·이동·HUD 자체는 사유가 아니다.
여러 필요한 필드는 실제 지원되는 한 호출로 묶고 동일 version 원문은 재사용한다. 부분조회 미지원이면 exact snapshot 한 번을 사용하고 entity마다 전체load하지 않는다. 저장 검증은 생략하지 않으며 별도 명시적 삭제 지시 없이 delete하지 않는다. 저장 없는 테스트는 원본 쓰기/불필요한 재조회 없이 작업 분기에서만 진행한다.

## STATE_IDENTITY

**진행 규칙은 항상 최신 프로젝트 소스:** 신규·기존 게임·같은 채팅·다른 채팅 재개 모두 현재 프로젝트 소스에 실제 등록된 최신 룰북의 담당 원문을 적용한다. 과거 세이브의 `rules_version`은 저장 당시 사용 이력이며 구판 룰북 파일을 요구하거나 그 판본으로 진행을 고정하는 조건이 아니다. GitHub main 변경이 업로드된 소스를 자동 교체하지는 않으므로 사용자가 소스를 교체하면 실제 읽은 최신 원문을 기준으로 갱신한다. 매 턴 전체 파일/원격을 재조회하지 않고 준비/재개·실제 소스 교체 때 한 번 확인한다.
**판본 기록과 정본의 구별:** 현재 배포 `RULESET.json`(또는 같은 배포 RULESET.md)의 실제 `rules_version`을 신규 checkpoint 최상위 `rules_version`에 기록한다. 기존 checkpoint 최상위 `rules_version`과 원문/해시는 이력으로 보존한다. 최초 정본 등록에는 생성 당시 배포 ID를 기록하지만 기존 정본의 생성 규칙판이 최신 checkpoint와 다르다고 오류로 보지 않는다. canon_ref의 ID/revision/file_sha256은 실제 원본을 계속 가리킨다. 규칙 갱신만으로 정본/세계나 과거 저장을 재작성·재해시하지 않는다. `TRPG-RULE-2026-11-17+sha256:<64자리>`는 실행 소스12개의 실제 경로/바이트 목록을 식별한다. 파일/해시를 확인할 수 없으면 ID를 추측하지 않고 확인 가능한 최신 원문으로 진행하되 정확한 배포 연결은 미확인으로 보고한다. `state_schema_version=TRPG_STATE_V2`는 별개의 서버 형식이다.
**기존 게임의 갱신·새 저장:** 현재 작업 상태가 있으면 과거 저장을 다시 로드하지 않는다. 현재 확정 HP/SAN/최대치·소유/소모·생사·세계/지도·지식/관계·완료 결과·받은 난수/선택·입력 대기를 보존하고 **아직 처리하지 않은 단계부터 최신 규칙**을 적용한다. 새 HP 산식으로 기존 최대치를 다시 생성하거나 소급 치료/죽음·보상·이벤트를 실행하지 않는다. 폐기된 구판 규칙은 앞으로 실행하지 않으며 과거 적용 사실은 남긴다. 기존 `runtime`의 지원되는 갱신 문맥에 적용 전후 rules_version(모르면 unknown)·전환 시점/관련 event와 보존한 열린 단계를 남긴다. 추가 top-level·SQL 컬럼이나 매 턴 기록을 요구하지 않는다. 같은 session/campaign에서 최신 verified parent 다음 **새 checkpoint**에 최신 ID와 완전한 누적 상태를 저장하고 STATE_COMMIT의 verify/read-back을 마친다. 이미 동결/제출한 저장 attempt는 원문 그대로 복구하고 이후 진행은 다음 저장에 담는다. 준비 화면/재생성·setup_bootstrap/play_start를 재실행하거나 규칙 교체 자체를 별도 자동 저장 경계로 만들지 않는다.

P1/P2/P3는 참가 슬롯, PC identity는 인물 식별이다. 참가 인원/실제 슬롯/대상PC가 일치해야 한다. 같은 슬롯의 새 인물은 새identity이며 과거 인물의 개인 배경·시트·성장·이미지를 상속하지 않는다. `pcs[Pn]`는 현재 통제 인물의 identity/상태를 소유하고 기존 `story_context`는 구/현 인물 ref·참가 시작/종료 이유/시점·플레이어별 캠페인 1회 인계 사용 및 각 identity의 실제 E 체험 이력을 보존한다. 세부 수납 이름은 실제 기존 기록을 따르며 P슬롯 재사용으로 과거 체험/기억을 합치지 않는다. 최종 참가 대상은 PC_REACHED_EVENT_CONTRACT를 따른다. 플레이어 공개 사실과 실제 전달된 PC별 극중 지식은 CORE_VISIBILITY에 따라 따로 보존한다.
**`permanent_cards_enabled=false`이면 카드 UUID/가입·클래스/장착·영구 성장 PC 링크/보상·효과를 생성/복원하지 않는다.** 값이 확인되지 않으면 기존 정본/체크포인트에서 먼저 확인하며 임의 ON으로 되돌리지 않는다. **ON에서만** 영구 카드 플레이어 ID는 PC identity/P슬롯과 별개의 UUID다. 자산·강화 카드의 실제 능력·소실/소모 및 영구 성장 적용/보상·장착은 09-cards.md의 CARD_SYSTEM_SCOPE·CARD_EQUIP_AND_ASSET·CARD_PLAYER_STORAGE를 따른다. **닉네임만으로 연결하는 신뢰형 운영**을 사용자 지시에 따라 적용한다. 중복 없는 닉네임을 입력하면 `public.card_login` 익명 RPC 또는 권한 있는 키퍼 연결로 영구 UUID·기본18·소유·성장을 확인한다. 로그인·비밀번호·추가 인증을 요구하지 않으며, **같은 닉네임은 같은 UUID이고 닉네임 사칭 가능성은 의도적으로 수용한다**. PC 연결 시 `trpg_cards.link_character`(또는 `public.card_link_pc`)가 그 시점의 성장 단계를 `applied_stats` 스냅샷으로 확정하고 같은 PC 재로드에서는 재적용하지 않는다. UUID/카드 소유·성장은 별도 영속 카드 DB에, PC 실물·동행·HP/SAN·실제 세계 상태는 종전 verified checkpoint에 둔다. 공개 `card_*`는 **원래 GM 세이브 RPC의 접근권을 바꾸지 않는다**. 두 저장 영역의 성공·실패를 혼동하지 않는다.
NPC/entity·원문·약속·물건·이벤트는 이름이 아닌 stable ref로 연결한다. 메뉴/대화/판정·중단 작업에는 현재 담당과 실제 선언 범위를 남겨 로드 후 자동 수락/실행하지 않는다. 이전에 형성/전달된 사건 연루와 완료한 확인도 보존한다.

새 독립 테스트는 새 campaign/session과 현재 실제 배포 rules_version·사용 원작/확정 입력·실제 사용한 생성 axis_name/retry_index를 기존 생성/이야기 문맥에 연결한다. 배포 RULESET.json은 신규 준비 전에 실제 읽으며 없으면 확인 가능한 소스/해시만 확인한다. 새 날짜 표제를 복사하거나 이전 저장 rules_version을 최신으로 바꾸어 검증을 가장하지 않는다. 로컬 파일 검증만 한 것과 서버 verified를 구별하고, 프로젝트에 예전에 업로드한 룰북이 GitHub main 갱신으로 자동 교체된다고 가정하지 않는다.

같은 배포의 RULESET.md는 RULESET.json과 동일한 rules_version을 담은 읽기용 메타데이터다. 프로젝트가 JSON을 조회하지 못하면 이 실제 파일로 배포 ID를 확인한다. 두 파일/실제 소스가 다르면 혼합 판본·정확한 ID 미확인으로 알리고 실제 최신 원문을 확인한다. 과거 판본 파일 확보를 진행 조건으로 삼거나 임의 최신 문자열을 생성하지 않는다.

## STATE_EXPERIENCE_CONTINUITY

저장 단위는 현재 수치뿐 아니라 지금까지 확정된 경험·작은 사실과 그 연결이다. 사건 제목/최신 요약만 남기지 않는다. 별명·농담·취향·작은 약속/거절·말투 변화도 실제로 성립했다면 중요도가 낮다는 이유만으로 버리지 않는다. 모든 대화 전문이나 내부 추론 과정을 저장할 필요는 없지만, 실제 발언·행동·확인된 결론과 출처는 다음 소유 영역에 남긴다. 정확한 표현이 관계/답변/퍼즐/선택을 바꾸면 실제 짧은 원문을 인용한다. 이 의무는 자동 저장에도 적용하며 수동 전용 스토리 파일 생성을 기다리지 않는다.

|---|---|
| story_context | 시간순 주요 인과/선택·작은 공동경험·채택/변경/거절한 목적·발견/누가 들었는지·관계/약속의 성립과 변경 근거·미해결 질문·인물 identity별 참가/종료/인계 이력과 E 직접 체험 |
| npc_contexts | 정식 인물 ref별 말투/상대별 호칭·존대/어휘/버릇·실제 발언 예·공동경험과 현재 태도의 이유·제안/수락/거절 범위·자기만 아는 것/누가 전달했는지·현재 위치/의도와 다음 행동 조건 |

| ongoing_consequences | 약속·준비의효력·위해/치료·화면밖진행·잔존조건·다음접점·이미실행/차단/취소한event |
이 재개 문맥은 실제 사실을 설명하는 자연어/구조화 데이터이며 경쟁 정본이나 미래 대본이 아니다. 수치·물건·합의·이벤트는 각 실제 상태ref와 일치해야 한다. 필요한 맥락은 현재 장면 밖에도 남기며 인물이 잠시 안 나온다고 버리지 않는다. 동일 사실은 정식 ref로 한 번 보존하고 변경/해소는 이전 사실을 지우는 대신 실제 변경 이유/시점을 잇는다. 이야기 맥락에 현재 HP·탄약 같은 경쟁 원장을 만들지 않는다. 소지/바닥/상자 위치·장전탄/예비탄·연료/손 점유는 실제 PC/물품 원장, 화재/수리의 경과/잔여 작업·적의 마지막 확보 정보는 해당 동적 상태를 가리킨다.
개인 지식은 **PC가 원래 아는 사실·플레이어에게 실제 전달/수령 확인한 범위·다른 PC에게 극중 공유된 범위**를 분리해 기존 `story_context`/PC 문맥에 남긴다. 해당 fact/source ref·identity·전달 수단/파일명·실제 판본/해시(확인했으면)·준비/전달/수령 확인 단계와 실제 공유 내용/화자·청자/시점을 연결한다. 파일 생성만으로 수령/극중 공유를 true로 기록하지 않고, 개인 전달 기록을 두 번째 게임 행동/판정 커서로 만들지 않는다. 기존 초기 기억이 전달 누락이면 실제 원문에서 해당 플레이어에게 보완하고, 재개 자체로 모두 공개하거나 실제 수령 확인을 초기화하지 않는다. 파일 유실 시 기존 동일 판본의 본인 정보만 재발급하며 다른 PC/정본 전문을 섞지 않는다. 새 최상위/서버 필드를 요구하지 않는다.
당면 목적·겪고 있는 상황/압력·함께 행동하는 사람·쓸 수 있는 준비/수단·다음 대응은 기존 story_context/scene_context/ongoing_consequences에 보존한다. 단서 목록만으로 현재 경험을 대신하지 않으며 이를 위해 새 서버 필드/저장 수단을 가정하지 않는다.
의사소통은 방향과 범위를 가진다. A가 B의 말을 이해함은 A가 그 언어로 발화함/B도A를이해함/모든의도를앎과 다르다. 실제 통했던 방식과 확인된 의미·아직 모르는 요구를 남기고 로드 뒤 미확인으로 낮추지 않는다.
제안/수락·소유/소지·공개/양도·준비/실행·노출/피해적용·관측/전언/추론·confirmed/inferred/unknown을 구별한다. 필드 부재·unknown·false·true도 서로 다르다. 기록의 각 사실은 실제 사건/발언 ref·시점/순서·인지자·확실성과 연결한다. 질문을 들음/이해함/동의함·플레이어가 읽음/PC가 앎을 합치지 않는다. 기록되지 않은 과거 감정/친밀감/대사를 추측하지 않는다.
변화가 생긴 때 해당 사실과 맥락만 갱신한다. 저장 직전 payload에서만 기준을 뽑아 자기검증하지 않고, 현재 작업 원문에서 중요한 값·관계방향·범위·출처·대기를 고정한 검증 기준을 만든다. `critical_state_registry/manifest`는 직렬화 **전** 작업 상태에서 실제 존재하는 보존 대상 ref/경로·영역별 범위를 고정한다. 수치만 비교하고 이야기/작은 기억·대기 영역을 통째로 빠뜨리지 않도록 각 실제 대상이 비교 기준에 포함됐는지 먼저 확인한다. 원래 없는 항목은 비해당/미확인으로 구별하며 채움용 빈 객체/가짜 기억을 만들지 않는다. 실제 read-back 원문과 정확한 canon_ref만으로 재구성한 논리 상태를 그 기준과 대조한다. 해시 일치는 바이트 보존이며 맥락/의미 충분성의 증명이 아니다.
첫 지문 전에 복원된 이야기·인물·현재장면을 적용한다. 이전 채팅 없이 이어쓰기 비교로 완료한 확인을 되묻는지, NPC말투/태도·목표/다음선택·준비/피해가 이어지는지 별도 평가한다. 값 비교 스크립트가 이 표현/적용 품질을 자동 검증하지는 않는다.
**누적 스토리의 공통 내용:** 두 기록의 범위는 HQ_SORTIE_STORY_ARCHIVE, 수동 2단계 절차/파일 연결은 STATE_COMMIT, 로드 순서는 STATE_RESUME이 소유한다. 스토리는 실제 플레이 기록을 장면/인과 순으로 자세히 풀어 쓴 누적 줄거리다. 분량·문단/사건 수 상한을 두지 않으며 최신 회차만 남기거나 중요 사건 몇 개로 축약하지 않는다. 각 작은 상황의 장소/확인 시각·참여 identity·관측/발언·선택/거절·시도와 실제 판정/결과·이동·물품 인계/소모·피해/치료·약속/관계 변화·해결/남은 질문을 실제 발생한 범위에서 잇는다. 적용된 값과 아직 입력/처리 대기인 것을 구별하고 마지막 게임 질문/선택지·각 PC의 현재 지점도 남긴다. 정확한 발언이 없으면 의미 요약이라고 표시하며 대사를 창작하지 않는다.
PC가 갈라진 구간은 각자의 시각/장소/인지자를 표시하고 실제 플레이 순서와 동시 진행 관계를 잇는다. 다른 PC가 겪은 내용이 파일에 있다는 이유로 극중 지식을 공유하지 않는다. 관측 사실·전언·추론·나중에 확인한 진상을 구별하고 정본의 미공개 비밀·미발생 사건·예정 결과·내부 추론을 줄거리로 옮기지 않는다. 파일은 소유자/키퍼용이며 기플레이한 분리 PC 정보가 포함될 수 있음을 표시한다. 새로운 서사나 게임 진행을 생성하는 단계가 아니다.
실제 전달된 개인 브리핑도 사실/인지자/극중 공유 범위를 구별해 보존한다. 전체 상태/정본·전체 스토리 파일은 소유자/키퍼용이며 개인 배부/공용 복기로 대신 열어 다른 PC의 미공유 내용을 노출하지 않는다.
이전 스토리 이후의 실제 추가 진행을 모두 수록한다. 최초 생성/구판 이관은 남아 있는 채팅·검증된 상태/원문·사용자 확정 기록에서만 복구한다. 원작 줄거리/정본의 미래 설계로 잃어버린 플레이를 채우지 않는다. 기록 공백·불명 시각/턴·상충과 확인 출처는 명시하고, 부분 기록을 전체 복원이라 부르지 않는다. 이미 읽은 대화가 장면 밖이라는 이유로 누락돼서는 안 된다.
필수 사실 누락/확실성 하락/맥락 모순은 복원 연속성 미검증/누락으로 보고한다. 서버 verified만으로 완전한 최신 복원이라 하지 않는다. 실제 기록·현재 상태·사용자의 명시 확인으로만 보완하고 부분 복구라는 이유로 이미 아는 사실을 초기화하지 않는다.
**열린 입력의 단일 소유:** `runtime.pending`에 대상 PC/인물·선언/action ref·처리 범위·판정 기능/난도/유불리·받은 실제 원값·미입력/수신했으나 미적용/적용 완료·행운/강행/카드 선택 대기를 구별한다. 전투 순서/잃은 차례·추격·광기의 남은 실제 행동 기회도 해당 실행 상태에 잇는다. `scene_context`의 마지막 대사/메뉴는 이를 표시할 문맥이며 독립된 두 번째 진행 커서를 만들지 않는다. 저장 안내/이동표를 마지막 게임 질문으로 덮지 않는다.
**용량/유실:** 현행 V2 `state_json` 한도는 UTF-8 5,242,880바이트다. 같은 정본 불변 전문·중복 사실/이미지 생성 프롬프트를 제거하거나 실제 ref로 연결할 수 있지만 고유 기억을 몰래 버려 맞추지 않는다. 그래도 넘으면 원격 저장 미완료와 범위를 알리고 지원되는 완전한 비공개 로컬 묶음으로 보존한다. 새 DB 모드를 발명하거나 요약을 완전 저장이라 부르지 않는다. 이미 대화가 유실됐다면 남은 실제 원문/상태에서 복구하고 없는 대사를 창작하지 않는다.


## HQ_SORTIE_STORY_ARCHIVE

**두 기록·용어의 소유 범위:** 수동 생성 스토리는 (A) **출격별 상세 스토리**와 (B) **본부 통합 출격 연대기**의 두 독립적인 파일 계열이다. 두 파일은 같은 확정 플레이를 서로 다른 범위로 보여 주는 비공개 참고 기록이며, 세계/HP/소지·종결/본부 인사·보상의 경쟁 원장이 아니다. 04-setup STORY_SCALE의 CHRONICLE은 한 현지 세계의 지속 챕터 규모이고, 여기서의 **본부 통합 출격 연대기**는 서로 다른 현지 세계/캠페인에 대한 영구 요원의 실제 여정 기록이다. **본부 OFF**에는 출격·귀환·영구 요원을 만들어 붙이지 않고 기존 캠페인별 STORY_SAVE만 유지한다.

**A — 현지 상세 스토리(본부 ON은 출격별·OFF는 캠페인별):** 본부 ON의 하나의 출격은 실제 본부 segment_id와 연결된 depart_after_actual_briefing 성공 이후의 현지 첫 경험에서 시작하여 해당 출격의 실제 return_segment 귀환이 성립한 지점에서 끝난다. 귀환 전이면 *진행 중*으로 표시하고, 사망·복귀 실패로 귀환하지 못했다면 확인된 현지 종결 및 미귀환 사실로 닫되 가짜 귀환을 쓰지 않는다. 같은 출격 안에서 CHAPTER_TERMINAL이 여러 번 발생해도 본부에 실제 귀환하지 않았다면 별개 출격으로 쪼개지 않는다. 같은 campaign_id에 여러 segment_id가 있으면 출격 경계별로 구분하며 다른 캠페인·독립 테스트를 단일 현지 기록에 섞지 않는다. 출격 *전* 본부 입단·브리핑/준비와 귀환 *후* 제이든·마틴·클라라·도미닉 교류는 A의 출격 외부이므로 아래 B에 싣는다.

**B — 본부 통합 출격 연대기(본부 ON):** 검증된 team_id와 영구 요원 UUID의 실제 소속·참가 구간을 기준으로 최초 본부 입장/입단 수락·거절/생활·교류/준비 → 실제 첫 출격 현지 경험 → 귀환·실패/본부 후속 교류·평가·보상·성장 → 다음 실제 출격 경험을 **한 권의 시간순 연속 서사**로 잇는다. 각 출격 장은 A의 같은 실제 장면·선택/판정·결과를 충분한 밀도로 포함하며 짧은 사건명/요약만으로 대체하지 않는다. 본부 사이 장면과 현지 출격 경험을 각 파일 계열 **내에서는 한 번씩** 싣는다. A/B 서로 다른 파일에 같은 실제 장면이 실리는 것은 사건 중복 적용이 아니다. 표시이름/P슬롯만으로 팀/요원을 연결하지 않고 검증된 UUID/team_id/segment_id 및 실제 참가 이력을 사용한다. 팀 변경 시 소속 구간을 표기하고 다른 팀·요원의 별도 경험은 연결 근거 없이 합치지 않는다.

**인지·비공개·근거:** 두 파일 모두 소유자/키퍼 전용이다. 다인 각 PC의 시각·장소·체험·발언 청자와 영구 요원이 본부에서 실제로 알게 된 정보를 분리한다. **소유자가 연대기 전체를 읽었다는 사실은 현지 PC 또는 다른 요원에게 비밀이 공유됐다는 뜻이 아니다.** 본부 기록은 권한 있게 확인한 실제 HQ 입단/교류/브리핑/귀환/평가/보상 이벤트나 신뢰 가능한 사용자 원문에서만, 현지 기록은 정확한 verified 캠페인/세션/정본과 실제 플레이 근거에서만 취한다. 비공개 정본 미발견 진상·NPC가 모르는 비밀·미발생 미래·미확정 대사/귀환/보상을 쓰지 않는다. 클라라의 극중 기록 공개는 06-play OPTIONAL_POST_CREDITS_VIEWS를 그대로 따른다. 기록 공백·불확실한 시각/출처·접근 불가 범위를 명시한다.

**증분·구판 분리:** 같은 A 출격 파일 계열과 같은 B 팀 연대기 파일 계열은 각각 직전 검증 UTF-8 전체 파일의 바이트 접두부를 그대로 보존하고 해당 계열의 마지막 수록 사건 이후 실제 진행만 덧붙인다. 새로운 출격은 A의 새 계열로 시작하되 B는 같은 팀의 실제 연속 관계가 확인되면 계속 잇는다. 동일 계열 내 기록 중복을 피하고 정정은 출처·정정 대상/이유를 추가한다. 본부/현지를 섞어 쓴 **구판 STORY_SAVE는 소급 편집·삭제/해시 개조하지 않는다.** 범위가 다른 두 새 계열을 최초 생성할 때 구판의 검증 가능한 부분을 출처와 함께 각 범위에 이관·중복 제거하고 구판 SHA·전환 이유·공백을 명세에 밝힌다. **새 계열의 첫 판본 이후부터** 그 계열의 접두부 불변을 적용한다.

## STATE_INTEGRITY

저장 경계에서 현재 full 논리 상태와 같은판본 정본/최신 의미유효 verified parent를 대조한다. session/identity/규칙판/정본SHA·참가슬롯·currentPC·턴/시간·세계변화·난수/미해결단계·장비/소유·진행성상태·학습/성장·마지막질문과 재개맥락이 일치해야 한다.
critical_state_registry와 manifest는 실제 활성 namespace/ref/내용을 가리켜야 하며 빈 이름 목록이 아니다. 같은 E/S·인물·위협에 runtime 요약과 world_delta·현재 경험 문맥이 있으면 현재값/관측 시점·단계가 서로 일치해야 한다. 실제 현재 원장 한 곳을 정하고 중복은 해당 ref의 투영/명시적 과거로 정리한다. 도움을 완료했는데 not_reached·전원 baseline으로 남기거나 지난 공격을 현재 활성 공격으로 두지 않는다. 원문/SHA 일치만으로 이 의미 충돌을 통과시키지 않는다. 불변 원문은 같은 정본/검증된ancestor에서만 복구하고 변하는 값을 과거snapshot으로 메우지 않는다. 현재/정본 사이 모순을 새 진실/동기로 합리화하지 않는다.
DB1의 6개 baseline/changed 집합·누적 delta·신규/취소/처리 event coverage 및 재개 문맥/실제 상태 참조를 확인한다. 저장 전 실제 의미를 대조할 때 **E의 세계 발동/차단/잔존 위험과 각 PC가 선언한 목적·현장 또는 실시간 원격 개입·직접 알게 된 사실**을 구분한다. 세계 해결과 별개로 참가 PC 전원의 현장 체험을 확인하며 한 PC의 해결은 다른 PC의 자동 지식/수락이 아니다. 검증된 기존 캐논 판본·world_delta/processed_event_ids·실물/부상/안전·저장 소유권을 보존하고 실제 read-back 없는 저장 성공을 주장하지 않는다.

## STATE_CHECKPOINT_RECAP

게임 시작과40배수 저장에서는 동일 version verified exact read-back을 재사용해 정본+전체 동적 상태를 대조한다. 수동/종료/로드도 이미 확보한 원문과 검증 결과를 재사용한다. 복기만을 위한 latest/list/추가 full load를 만들지 않는다.
현재 장면 밖을 포함한 NPC/단서/장소/경로·활성/취소/휴면위협·미해결약속·PC/난수/입력대기·이야기/인물/장면문맥과 출처가 있는지 확인한다. 잘린 원문은 실제 누락 범위를 확보하고 전체완료라고 하지 않는다. 변경없는 불변 전문을 매40턴 새로 생성하지 않는다.
검증 원문을 바탕으로 현재 작업의 관련 맥락/다음조건을 정리하되 요약으로 원본을 대체 저장하거나 미래40턴을 생성하지 않는다. 읽기/대조는 시간·사건·피해·성장을 다시 적용하지 않는다. 실패 시 현재 확인 가능한 상태로 복기하고 verified 복기라 부르지 않는다. 비밀 복기 보고를 공개하지 않으며 무손실 기억 보장을 주장하지 않는다.

## STATE_COMMIT

캠페인당 Single Writer. 같은 저장 요청은 같은 attempt로 처리한다. 신규 setup_bootstrap 전 원본 .md와 같은 내용을 Supabase 비공개 trpg_private.gm_canon_documents의 (campaign_id,canon_id,revision)에 등록해 전체 내용·SHA-256을 read-back한다. 기존 revision 충돌 시 덮어쓰지 않고 동일성만 확인한다. 별도 필드를 V2 checkpoint에 추가하지 않으며 이후 매 체크포인트에서 canon 전문을 다시 전송하지 않는다.
1. 수동/채팅 이동 저장은 지금의 입력 대기·전투/대화 중간 지점에서 자른다. 장면을 끝내거나 PC 답/이동·시간을 대신 처리하지 않는다. STATE_INTEGRITY와 직렬화 전 경험/맥락 기준을 고정하고 실제 모드의 별도 payload를 만든다. 최신 verified+1 version·event_id=<session_id>:cp<version>·parent를 확인한다. 작업 상태를 축소하지 않는다.
2. 쓰기 전에 UTF-8 state_json 원문·session/version/event·SHA-256을 동결한다. 같은 attempt 도중 다른 상태로 재직렬화/재번호하지 않는다.
3. 정확한 계약으로 pending commit하고 raw 원문/hash/식별자를 확인한다.
4. 동일 원문과 의미/parent/manifest를 verify한다.
5. 같은 version의 verified 원문을 exact read-back하여 문자열·SHA-256·session/version/event/parent와 정본 결합 의미/재개맥락을 대조한다. 모두 확인돼야 저장 완료다. HTTP성공/파일명/해시문자열만으로 완료라 하지 않는다.
6. 같은 원문으로 STATE_CHECKPOINT_RECAP을 수행하고 이후 최신 미저장 변화는 보존한다. exact load 요건을 충족한 read-back을 중복 조회하지 않는다.
idempotent_replay는 같은attempt 존재를 뜻하므로 실제 verify/read-back 상태를 이어 확인한다. cadence 성공은 검증 뒤 반영하고 payload 내부pending을 사후 수정/재해시하지 않는다. API 객체/문자열/hash 직렬화는 서버 계약대로 하며 가정하지 않는다. 경험 비교 미실행/실패는 서버 verified와 별개로 복원 연속성 미검증을 표시한다.
현행 V2의 연결 계약은 `public.trpg_v2_commit(session_id text, version bigint, event_id text, attempt_id text, parent_version bigint, parent_sha256 text, state_json text, state_sha256 text)` → `public.trpg_v2_verify(session_id text, version bigint, event_id text, attempt_id text, state_sha256 text)` → `public.trpg_v2_load_version(session_id text, version bigint)` 순서다. 실제 SQL 호출 시 각 인자명 앞에 `p_`가 붙고, 순서는 위와 같다. 원문 UTF-8 바이트 SHA-256를 동결하고 서버가 같은 원문/parent를 검증한다. `trpg_v2_load`는 최신 verified만, `trpg_v2_list`는 각 세션 최신 verified 메타만, `trpg_v2_inspect_pending`은 해당 세션 미확인 시도만 반환한다. 정상 재개는 pending이 아닌 verified를 선택한다. 채팅 이동용 지정 버전/원문과 비공개 파일 인계는 STATE_RESUME을 따른다. 인증 없는 Data API·일반 authenticated·anon에 데이터/RPC 권한이 없으며 권한을 풀어서 통과시키지 않는다.

### 수동 저장 2단계와 출격별·통합 연대기 파일

1. **상태 저장:** 명시 수동 요청이면 위 1~6으로 현재 상태를 검증하고 기존 정본 원문/SHA·접근을 확인한다. 기존 story_context.story_save.latest_created는 하위 호환을 위해 해당 캠페인/출격의 기존 STORY_SAVE 참조로 유지한다. request는 request_id·대상 session/version·이전 현지 스토리 SHA·확인한 끝 ref·예정 파일/명세·stage=awaiting_input을 수납한다. **본부 ON에서는** 확인된 team_id·segment_id·참가 영구 요원 UUID, 이전 통합 연대기 파일/명세 SHA·끝 ref를 같은 request 또는 기존 story_save의 지원되는 하위 참조(예: hq_chronicle_latest)에 함께 연결한다. 실제 스키마가 허용하지 않으면 외부 비공개 파일 명세에서만 연결하며 새 필드의 저장 성공을 가정하지 않는다. request_id는 게임 event/processed_event_ids도 두 번째 runtime.pending도 아니다. 자기 checkpoint SHA는 동결 payload에 넣지 않고 read-back 뒤 명세에서 연결한다. 기존 문맥/필드를 덮거나 새 V2 최상위·테이블·RPC를 만들지 않는다.
2. **완료 알림 후 대기:** 실제 정상 저장 결과와 이동표를 먼저 주고 `스토리 세이브 생성` 등 추가 입력을 안내한 뒤 응답을 끝낸다. 이 응답에서 스토리 파일을 미리 작성하지 않는다. 이어진 명시 생성/계속 입력으로만2단계를 시작하며 다른 게임 행동·거절/유보를 동의로 해석하지 않는다. 수동 저장 요청에 스토리까지 미리 언급했어도 두 단계 사이의 추가 입력은 받는다. 이 메타 대기는 마지막 게임 질문·행동권/판정 대기를 대체하지 않는다. 이후 게임을 진행해도 스토리 대상은 완료한 그 저장 경계에 고정하며 경계 밖 새 사건을 끼우지 않는다. 더 최신 경계를 원하면 정상 수동 저장으로 새 요청을 만든다.
3. **누적 작성:** 추가 입력 뒤 대상 저장/정본·출격 segment·실제 현지 기록 및 권한 있는 본부 이력, **각 계열의 직전 전체 파일/명세 SHA와 마지막 event**를 독립적으로 대조한다. HQ_SORTIE_STORY_ARCHIVE에 따라 본부 OFF/ON 모두 A 현지 상세 기록을, 본부 ON이면 B 팀 통합 출격 연대기도 작성한다. 각 계열의 직전 전체 UTF-8 바이트를 그대로 접두부로 보존하며 마지막 수록 ref 이후부터 대상 저장/확인된 HQ event 경계까지의 **실제 새 진행만** 덧붙인다. 각 추가부에는 현지 source_refs·PC별 시각/순서·출격/귀환 상태·대상 session/version/SHA·canon_ref·권한 있게 확인한 HQ ref/사건·직전 파일 SHA·끝 지점을 둔다. B의 이전 캠페인/팀 연속 근거가 확인되지 않으면 임의로 합치지 않고 공백/부분 기록으로 구별하며 A 생성까지 실패시키지 않는다. 미래 저장·다른 분기/폐기 테스트·미발생 사건은 포함하지 않는다. 동일 계열의 중복 사건/재굴림/재적용은 없고 정정은 출처와 이유를 추가한다. 구판 혼합 문서의 최초 계열 분리만 HQ_SORTIE_STORY_ARCHIVE의 이관 규칙을 적용한다.
4. **파일 검증/전달:** 본부 OFF의 캠페인별 기록과 기존 본부 ON 단일 출격 STORY_SAVE_<campaign_id>_r<N>.md/기존 명세 format=STORY_SAVE_V1은 유효하게 수용한다. 본부 ON의 신규·다중 출격 A는 STORY_SAVE_<campaign_id>_<segment_id>_r<N>.md, format=STORY_SAVE_V2를 사용하고 B는 HQ_SORTIE_CHRONICLE_<team_id>_r<N>.md, format=HQ_SORTIE_CHRONICLE_V1을 쓴다. 각 파일에 같은 basename의 .manifest.json을 별도 제공한다. 각 명세에는 scope, campaign_id/segment_id 또는 team_id/agent_ids, request_id·revision·파일명·UTF-8 byte_length/file_sha256, 직전 같은 계열 파일/해시/대상 저장, 이번 현지 session/version/state_sha256/canon_ref·HQ event ref/검증 출처, 출격/귀환 여부·수록 시작/끝·추가 source_refs·공백/상충·완전/부분 수록 상태를 기록한다. 이전 파일의 바이트 접두부/해시·같은 계열 사건 중복·출격 경계·끝 STATE의 수치/소유/입력 대기 정합성을 검증한다. 명세는 자기 SHA를 넣지 않는다. 크기 상한에 실제 도달한 경우에만 순서/파일별 SHA/전체 SHA의 분할 파일로 전달하고 발췌를 전체라 하지 않는다. 같은 요청 재시도는 계열별 검증된 같은 판본/파일을 재전달하고 새 판본·중복 추가를 만들지 않는다. 두 계열의 생성·검증·전달 성공/실패는 **각각** 알리고 한쪽 실패로 다른 성공을 취소하지 않는다.
5. **보관과 다음 저장:** A/B 전문과 명세는 소유자의 비공개 파일/프로젝트 소스에 보관한다. 새 채팅에서 접근할 수 있는 최신 전체 A·명세와 본부 ON의 최신 전체 B·명세를 함께 보관/첨부하도록 안내한다. 실제 연결된 비공개 도구의 권한/기능이 없으면 업로드·영속 보관 성공이라고 하지 않으며 DB에는 스토리 전문을 복제하지 않는다. story_save.latest_created는 기존 A 참조로 유지하고 B는 확인된 지원 하위 참조 또는 외부 명세로 따로 연결한다. 다음 정상 저장이 **실제로 검증한** 참조만 수납하며 스토리 파일 때문에 새 checkpoint를 추가하거나 기존 verified 원문/해시를 고치지 않는다. DB에 awaiting_input이 남아 있어도 해당 request·정확한 대상 저장/HQ 출처와 부합하는 파일/명세가 계열별 완료 근거다. 본부 terminal·귀환/평가/보상은 다시 실행하지 않는다.

**실패·구판:** 상태 저장 실패는 STATE_SAVE_FAILURE_CONTINUE로 구별한다. 완전한 로컬 상태/정본 묶음을 확보한 뒤 사용자가 추가 입력으로 스토리를 요청하면 그 실제 파일 SHA를 대상으로 연결할 수 있으나 서버 verified라고 하지 않는다. 기준 상태/이전 스토리가 유실되면 임의 재생성·접두부 생략으로 완전 누적을 가장하지 않는다. 확인 가능한 부분 기록은 공백/누락 범위와 마지막 유효 판본을 명시한다. 스토리 생성/파일 전달/보관 중 하나만 실패해도 정상 상태 저장까지 실패/취소됐다고 하지 않으며, 완료/미완료 단계를 따로 알리고 같은 요청으로 복구한다. 기존 게임에 스토리가 없으면 없는 이력을 꾸미지 않고 첫 수동 2단계에서 실제 기록으로 초기 누적본을 만든다. 한 계열의 원문/근거가 부족하면 부분 수록·미완료로 구별하고 다른 계열의 성공은 유지한다. 자동 저장에는 이 파일 생성/추가 입력 절차를 소급 실행하지 않는다.

## STATE_VERIFIED_OWNER_AUDIT_AND_GITHUB_BACKUP

소유자의 명시적 비공개 감사는 플레이 밖 읽기 전용이다. Supabase의 정확한 canon revision과 session/version verified 체크포인트를 조회해 원문·SHA-256·정본 참조·누적 상태를 확인한다. 확인하지 못한 항목과 권한 제한을 사실대로 알린다.
이 절의 GITHUB_BACKUP은 구판 호환 ID다. **모든 정상 저장 경계(setup_bootstrap, play_start, 40턴, 수동, 종결)는 Supabase commit → verify → 동일 version exact read-back만 수행**한다. GitHub verified snapshot·MANIFEST·INDEX·REVIEW 등 추가 미러를 생성/갱신하지 않고 github_backup_pending도 새로 만들지 않는다. 정본 원문은 신규 캠페인/개정 때만 저장하며 매 체크포인트에 중복 쓰지 않는다.
과거 private GitHub 백업·비상본은 삭제하지 않고 역사 자료로만 보존한다. 공개 GitHub 저장소는 룰북/검증/배포 ZIP 전용이다.

## STATE_GITHUB_FAILOVER_PROTOCOL

구판 호환 절 이름이다. **GitHub 자동 백업·비상 체크포인트 저장·failover는 폐지**한다. Supabase 장애/차단/검증 실패 시 STATE_SAVE_FAILURE_CONTINUE와 STATE_RECOVERY로 현재 작업 상태·고정 attempt 원문·마지막 확인된 verified를 보존하고 공식 Supabase 계약으로만 재시도한다. 새 private GitHub JSON/meta/manifest를 만들지 않는다.
Supabase 읽기가 불가능하면 소유자가 제공한 동일 SHA 비공개 .md와 현재 작업 상태만 확인 가능한 범위에서 사용한다. DB 최신 버전이 불명확하면 완전 복원이라 말하지 않는다. 기존 GitHub 사본은 사용자가 과거 백업 대조를 명시적으로 요청한 때에만 읽기 전용으로 살펴보며, 자동 승격·재작성·삭제하지 않는다.
## STATE_SAVE_FAILURE_CONTINUE

세이브 실패는 게임 진행을 막지 않는다. setup_bootstrap/play_start/periodic/manual/terminal 모두 현재 상태가 있으면 시작·진행·종료를 계속한다. 재개 승인/실패 수락을 반복 요구하지 않는다. 실패·미확인을 저장완료/새채팅복원가능으로 표시하지 않는다.
최초 실패·상태변경·수동저장 결과·채팅이동 요청 때 마지막 실제 verified 지점과 미완료를 짧게 알린다. 매응답 같은 경고/자동재시도를 반복하지 않는다. 다음 정상 경계/수동요청/실제복구 때 재시도한다.
이미 제출한 pending 원문/hash/version/event는 동결하고 이후 진행은 별도 변경으로 보존한다. 연결 복구 시 기존attempt를 대조/정리한 뒤 그동안 진행한 최신 상태를 별도 체크포인트로 저장한다. 늦게 끝난 과거attempt를 현재까지 저장됐다고 하지 않는다.
충돌/여러작성자는 원격쓰기·자동병합을 보류하고 현재 작업 분기는 보존한다. 실제 유실된 수치/정본/판정은 관련 결과만 복구하며 저장장애와 구분한다. 원문/맥락이 실제 남아 있지 않으면 복원됐다고 하지 않는다. 종료 저장 실패도 결말/후일담을 막지 않는다. 채팅을 옮기려면 마지막 verified의 정확한 시점과 이후 미저장 범위를 구별하고, 실제 지원되는 전체 비공개 로컬 내보내기는 STATE_RESUME에 따라 제공한다. 실패한 최신 상태를 과거 verified 번호로 표시하지 않는다.

## STATE_RECOVERY

pending 뒤 verify/read-back 중단은 일반 일시 오류에 한해 같은 version/event/원문으로 자동 재시도 최대1회. 명시적 안전 차단은 우회하지 않는다. 실패로 난수/사건을 다시 실행하지 않는다.
orphan pending은 최신verified+1(없으면1),event규칙·exact원문/hash·의미/parent/manifest 연속성을 모두 확인한 뒤 같은 원문으로 verify를 완결한다. 여러 충돌pending/버전gap/다른원문/손상은 자동 승격·폐기하지 않는다. checkpoint_write_recovery_required로 남기고 현재 플레이는 계속한다. pending은 verify 전 정상재개 정본이 아니다.

## STATE_RESUME

새채팅/명시로드/실제상태유실 때 적용한다. 현재 상태가 있는데 저장만 실패했다고 재로드하지 않는다. 저장은 지정한 실제 상태를 복원하고 진행 규칙은 STATE_IDENTITY에 따라 **현재 소스의 최신 룰북**을 적용한다. 저장 버전 선택과 룰북 버전 선택을 혼동하지 않는다.
**신규 의미 복원 순서:** (1) verified 원문·canon revision/SHA·누적 coverage, (2) `world_delta.drivers`의 주요 E와 연관된 개체의 **실제 세계 상태**, (3) `story_context.main_track_by_pc` 또는 구판에 실제 남아 있는 PC별 목표/지식 출처·선택한 S/작은 활동, (4) `pcs/runtime/scene_context/ongoing_consequences`의 구조 가능성·물리 경과·열린 행동/이동·장비/치료, (5) 현재 PC에게 공개 가능한 고정 HUD의 순서로 재구성한다. 세계 E의 완료와 PC별 직접 체험은 서로 다른 사실로 비교하고 현재 문맥의 명칭만으로 누락·S를 E로 승격하지 않는다. **구판 verified**에서 `current_carrot/main_goal_ref/active_main_goals` 등 서로 다른 이름이 확인되면 실제 정본 E-ref·PC의 관측/수락과 원문 근거가 일치하는 범위만 새 표준 문맥에 연결한다. 부재/불일치를 임의 추정해 채우거나 저장된 원문을 고쳐 쓰지 않는다. 실제 새 체크포인트의 검증된 누적 변화부터 적용한다. 화면 밖 위해의 시각·대기 판정·확정 피해를 로드 때문에 다시 진행시키지 않는다.

1. 실제 연결·소유권·session을 확인하고 표시이름/P슬롯만으로 선택하지 않는다. **종료 상태의 본부 OFF는** 기존 남은 엔딩/다섯후일담을 복구한다. **본부 ON은** 검증된 현지 종료 뒤 현재의 **실제 본부 귀환 단계(제이든 동기화실 대화 → 실제 마틴 면담·평가 → 플레이어가 요청한 경우만 클라라 후일담 열람)**와 미열람/열람된 편을 구별하여 복구한다. 종료 상태를 현지 위험/PC 행동권으로 재진입시키거나 클라라 요청 없이 후일담을 자동 출력하지 않는다.
2. 이동표/사용자가 session·version·SHA를 지정했으면 그 **정확한 verified version**을 `trpg_v2_load_version`으로 읽는다. 지정이 없을 때만 해당 session의 최신 hash-valid verified를 선택한다. orphan pending은 STATE_RECOVERY로 확인하되 지정한 과거 버전을 자동 최신으로 바꾸지 않는다. DB1은 같은정본 전체SHA/판본/필수절/coverage를 확인하고 전체 누적world_delta·new_entities·tombstones·processed_event_ids와 PC/실행/재개문맥을 결합한다. LEGACY_FULL은 원문을 유지한다.
3. **두 계열의 누적 스토리 전체 조회:** 지정 상태의 story_context.story_save.latest_created/request, 실제 이동표/첨부 및 대상과 일치하는 완료 명세를 대조한다. A는 정확한 campaign/segment·session/version/state_sha256에 대응하는 최신 **전체 출격별 스토리/명세**를, 본부 ON에서는 B의 실제 team_id/영구 요원 참가 구간·기록 끝 HQ event/이전 캠페인 연속에 대응하는 최신 **전체 통합 연대기/명세**도 별도로 읽는다. 파일/명세 SHA·바이트 길이·이전 같은 계열 접두부·수록 끝·해당 HQ/현지 출처를 대조한다. 명칭 유사·수정 시각·검색 발췌로 전체 조회를 가장하지 않고 필요 범위를 모두 읽는다. 복원할 지정 시점보다 미래에 발생한 B의 사건/타 출격은 현지 PC의 과거 지식·현재 수치로 적용하거나 공개하지 않는다. 한쪽 계열이 없거나 손상됐으면 그 계열의 마지막 유효 범위와 story_source_required를 분리해 알리고 다른 원장/파일의 복원을 취소하지 않는다. 예전 STORY_SAVE_V1만 있으면 그 검증 범위로 재개하되 본부 전체 출격 연대기라고 부르지 않는다.
4. 첫 설정의 `permanent_cards_enabled`와 종속 성장 모드를 실제 정본/상태에서 복원하고 OFF이면 카드 로그인/장착·보상/성장을 실행하지 않는다. STATE_CHECKPOINT_RECAP/STATE_EXPERIENCE_CONTINUITY로 수치·각 스토리 계열의 검증된 인과/작은 상황·관련인물의말투/태도/이유·현재장면/마지막질문/확인된의미/입력대기를 함께 복원한다. 최초 장면 전에 적용한다. 정본 전체 확인은 PRIVATE_CANON_PERIODIC_REVIEW와 같은 원문을 재사용한다. 스토리 속 옛 수치/위치는 당시 이력이며 현재값은 지정 STATE가 소유한다. 모순은 출처 대조/확인으로만 보완하고 스토리 문장으로 verified 현재값·발생 사실을 임의 덮지 않는다. PC별 인지 범위도 그대로 지킨다. 개인 브리핑의 전달/수령 확인·극중 공유 단계를 복원하고 공통 로드 지문에 미공유 본문을 섞지 않는다.

## STATE_COMPATIBILITY

**2026-11-13 신규 PC HP 경계:** 당시 판본에서 생성·확정된 PC의 시작/현재/최대 HP는 `floor((최종 CON+최종 SIZ)/10)+1`로 **한 번** 확정된 과거 사실이다. 영구 성장 ON이면 PC 최초 링크에서 검증된 적용 특성값을 따른다. 이전에 확정된 PC·같은 PC의 재개/재링크·기존 verified 세이브/캠페인·NPC/적/동물 HP에는 소급 적용하거나 +1을 중복 지급하지 않는다. 현재 HP 변화는 실제 피해/치료만 반영하고 이후 중상·생사/치료와 적의 피해 처리는 최신 담당 원문을 따른다. 저장 스키마·RPC를 추가하거나 과거 원문을 수정하지 않는다.
