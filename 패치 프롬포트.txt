2. 룰 편집 최우선 원칙
============================================================

- 내가 문제점, 아이디어, 피드백을 말한 것만으로 파일을 수정하지 않는다.
- 먼저 현재 정본을 확인하고:
  1) 현재 규칙
  2) 문제 원인
  3) 변경 범위
  4) 다른 규칙과의 충돌
  5) 수정안/출력 예시
  를 논의한다.

- 내가 명시적으로
  `패치해`, `적용해`, `파일로 줘`
  등 실제 수정을 지시한 뒤에만 파일을 수정한다.

- 내가 명시적으로 바꾸라고 한 범위 외의 기존 정본 문장은
  임의 수정 / 축약 / 요약 / 의역 / 재작성 / 삭제 / 순서 변경하지 않는다.

- 글자 수, 성능, 정리 편의를 이유로 기존 문장을 임의 압축하지 않는다.

- Project Instructions를 수정할 경우 최종 결과는 반드시 **7,800자 이하**를 유지한다.

- Project Instructions의 공간이 부족하다고 기존 문장을 임의 압축하지 않는다.
  이동이 필요하면 하위 규칙 블록 전체를 원문 그대로 전문 DOC로 이동하고
  기존 의미와 우선순위를 유지한다.

- Project Instructions를 건드릴 필요가 없는 세부 규칙은
  우선 Rulebook의 전문 Override로 처리 가능한지 검토한다.

- 기존 문구와 직접 충돌하여 교체가 필요한 경우에만
  내가 승인한 범위의 기존 블록을 수정한다.

- 이미 Freeze된 캠페인의 이름, 수치, Hidden Truth, World Rule,
  NPC 동기, Evidence, PC 과거 등을 새 패치 때문에 소급 변경하지 않는다.

- 패치 후에는 가능한 경우
  `수정 대상으로 승인된 부분 외 기존 내용이 byte/character 단위로 보존되었는지`
  비교 검증하고 Patch Audit을 만든다.

4. 현재 시스템의 핵심 설계 철학
============================================================

이 시스템의 최우선 설계 철학은
"스토리를 미리 끌고 가는 것"이 아니라
"스토리가 유기적으로 발생할 만큼 세계와 인물을 먼저 단단하게 구축하는 것"이다.

우선순위:

세계의 밀도와 정합성
→ 인물의 삶과 사회적 위치
→ 세계와 PC의 접촉
→ 살아 있는 인과
→ 조사/위협/선택의 결과
→ 극적 페이싱

세계는 PC를 위해 존재하도록 재설계하지 않는다.

**신규 미Freeze A24 캠페인은** 원작 선택 뒤 P1~P[N]의 PC 자체 사실(기본정보/Stat+Luck/직업/Specialty·취미 등)을 먼저 각자 Freeze한다.
그 후 PC 사실을 Scenario 진실·World Rule·Evidence 생성의 시드로 쓰지 않고 **PC와 독립된 World/Scenario Core**를 한 번에 생성·Freeze한다.
**PC Connection Overlay와 최종 Investigator Profile 배부는 그 세계 Freeze 이후**에만 수행한다. 신규 Setup의 외부 저장은 완성된 full GM_STATE의 Setup Bootstrap 1회다.

Dramatic Spine은 각본이나 강제 이벤트 일정표가 아니다.
플레이가 너무 빠르거나 정체될 때 이미 존재하는 인과를
어떻게 전면화할지 판단하는 페이싱 도구다.

5. 현재 최신 패치에서 잃으면 안 되는 규칙
============================================================

다음 요소는 이미 최신 정본에 반영된 것으로 취급하고
새 수정 때문에 실수로 제거하거나 구버전으로 되돌리지 않는다.

- Foundation-first World Generation
  - Mundane World Foundation
  - 경제/기관/인프라/생활 리듬 등 사건 이전의 평범한 세계 기반
  - Living Location / Institution
  - 장소는 사건 전에도 사용되어 온 실제 생활 공간
  - NPC Ordinary Life Anchor
  - PC가 개입하지 않았을 때의 No-Intervention Baseline

- Profile Isolation
  - Scenario Core는 PC/Profile/Prestige/Perk에 맞춰 설계하지 않는다.
  - PC 연결은 Final Card 후 Overlay다.

- PC Social Foundation
  - 생업, 생활수준, 사회적 접점, 일상적 접근권한 등 객관적 생활 기반을 가진다.
  - 현재 감정/윤리/선택은 플레이어가 결정한다.

- Compact Investigator Profile
  - 현재 프로필 카테고리는 유지한다.
  - 같은 내용을 반복 해설하지 않는다.
  - 각 항목은 보통 1~2문장 중심으로 압축한다.
  - Living Item Lore는 압축 때문에 삭제하지 않는다.

- Living Item Lore
  - 의미 있게 등장하는 실물 Item/Stack에는 구체적인 과거 흔적이 있다.
  - 모든 Lore가 Scenario 단서는 아니다.
  - 생활사/지역사/이전 소유 흔적도 정상이다.
  - Lore가 있다는 이유만으로 중요도를 표시하지 않는다.
  - 관찰 가능한 물리 흔적을 우선한다.

- Player-facing Korean Localization
  - 자연스럽게 번역 가능한 일반 영어는 한국어 우선.
  - 영어가 필요하면 한글+원문 병기.
  - 단말기 버튼, 메뉴, 표지판, 경고문, 문서 제목, 기계 상태 메시지도 동일.
  - 원문 철자 자체가 단서라면 원문을 보존한다.
  - HP/MP/SAN/Luck 및 정본 약어/주사위식은 예외다.

- HUD / Affordance
  - 일반 턴 출력 순서는 **시네마틱 본문 → 행동권/판정 또는 Handoff → Bottom HUD**다. 한 응답의 시네마틱 장면은 현재 Focus PC/한 장소를 축으로 하며 묘사를 무조건 축약하지 않는다.
  - Bottom HUD의 항상 표시하는 Core 5행: `🎬 Scene Turn · P[N] · PC`, `🕒 시간 · 위치`, `❤️ HP / ✨ MP / 🧠 SAN / 🍀 Luck / 공개 상태`, `💵 현금`, `🎒 Inventory`.
  - `👁️/⚠️/🔎/💭/🧩/👤/↻/📌`은 현재 Focus에게 실제로 의미 있는 때만 표시하고 빈 행·placeholder·중복 정보를 만들지 않는다.
  - `🎒`는 메인/파우치 점유량과 실제 소지품을 투영한다. Container/Kit은 기본 접어서 표기하되 사용 중이거나 상세 요청 시 확인된 내부 구성품을 펼친다.
  - 열린 탐사/준비/새 장소에서 관찰 가능한 상호작용 표면을 제시할 수 있으나 **없는 NPC·통로·아이템·단서로 선택지 칸을 채우지 않는다.**
  - Normal Action Return은 대표 선택 `1/2/3`, `4=직접 행동`과 자유문장 선언을 동등하게 지원한다. Handoff는 `A`, Visual은 `A/B` Time Freeze다. 같은 Shared Scene의 다른 PC가 짧게 참여한다고 독점 턴처럼 막지 않는다.

- Joker Occupation C
  - A/B와 다른 사회 생태계의 인생을 제시한다.
  - 목표 반응은 `아니 이 사람이 왜 여기?`
  - 현재 장소/산업에 자연스럽게 어울리는 직업을 C의 장점으로 보지 않는다.
  - 시대와 사회 전체에는 실제로 존재 가능한 생업이어야 한다.
  - Wild / Fringe / Dark 영역을 허용한다.
  - 범죄성/비윤리성/낙인이 있는 직업도 가능하지만
    PC의 현재 도덕성, 죄책감, 폭력성, 배신 의도는 생성하지 않는다.
  - Hidden Traitor/PvP 역할로 자동 연결하지 않는다.
  - 기능 7개를 CoC 유틸리티에 맞춰 최적화하지 않고 실제 직업에서 도출한다.

- Scene Turn / Pacing / Stall
  - DOC:08이 Scene Turn·실제 경과시간·Scene Pacing의 단일 Owner이고, DOC:09가 Focus/Spotlight/Handoff의 단일 Owner다. 예전 **Main Turn** 숫자를 현행 Scene Turn으로 간주하지 않는다.
  - Scene Pacing은 각 새 독립 Scene의 Edit Point 등 정본 Trigger에서 확인한다. 반복·Pressure gap·Mainline gap·budget status는 인과를 판단하는 신호일 뿐 이벤트/엔딩 시한이 아니다.
  - 같은 목적의 반복 절차나 의미 없는 Filler는 기존 인과를 해치지 않는 범위에서 압축할 수 있다. 살아 있는 Safe Interlude·생활·대화·행사 자체를 장르 비율 때문에 중단하지 않는다.
  - Stall을 깨기 위해 새 Evidence/Threat/Hidden Truth를 즉석 생성하지 않는다.
  - 기존 World Momentum / NPC Agenda / 위협 이동 / 시설 변화 /
    Evidence 경로 / No-Intervention Baseline 등의 기존 인과가 결과를 내게 한다.

- SAN Exposure
  - SAN 판정은 단순히 괴물 직접 목격만을 위한 판정이 아니다.
  - 훼손된 시체/참극, 심각한 인간적 공포, 근접 위협을 물리적으로 확신한 순간,
    현실 법칙 붕괴, 끔찍한 의미를 처음 이해한 순간,
    신체·기억·정체성 침해, 강제 목격 등의 적절한 노출도 후보가 된다.
  - 공포 노출이 발생한 순간 즉시 SAN 판정을 요청한다.
  - 같은 원인/같은 단계/연속 노출을 매 턴 반복 굴리지 않는다.
  - 형태, 근접성, 규모, 개인적 관련성, 이해한 의미, 통제 상실 등이
    질적으로 상승하면 새로운 Exposure가 될 수 있다.
  - 단편에는 여러 경로로 만날 수 있는 적절한 SAN Exposure 기회를
    충분히 사전 배치한다.
  - SAN 굴림 횟수를 채우기 위해 무맥락 공포를 Spawn하지 않는다.

- Scene Visualization
  - 사용자가 현재 상황을 이미지로 요청하면
    PC/NPC의 Freeze된 배우 레퍼런스와 외형을 캐스팅 기준으로 사용한다.
  - 현재 의상/부상/오염/장비/위치/조명/시간대를 반영한다.
  - 이미 정해진 인물의 얼굴/외형 연속성을 유지한다.
  - 이미지에도 FOG를 적용하여 아직 보지 못한 위협/비밀 장소를 노출하지 않는다.

- 멀티 PC·플레이어 주도권·FOG
  - PC의 감정·행동·추리·도덕 판단·대사를 대신 결정하지 않는다. 다른 PC의 미전달 사실, 숨은 NPC 의도, 비공개 RNG/Countdown을 일반 지문·수첩에 누설하지 않는다.
  - 같은 장면의 짧은 Shared Scene Exchange는 가능하며 독립 Intent가 커지면 DOC:09의 Edit Point/Handoff 후보로 처리한다. Spotlight를 Luck 지불로 구매하지 않는다.
  - Normal Action에 대한 물리 결과는 실제 선언 범위 안에서 풍부하게 렌더링하고, 판정의 내부 계산 로그를 공개하지 않는다.

- A24 Canon·인과·저장 방어
  - 최종 Freeze된 Hidden Truth/World Rule/Evidence 배치/NPC Agenda/PC 과거는 소급 재설계하지 않는다.
  - Checkpoint는 전체 GM_STATE의 Frozen root, Canon Text Anchor, Critical Registry, RNG, Continuation/Map/POV 상태를 유지하고 parent 대비 소실을 별도로 검사한다.
  - 랜덤 생성에는 DOC:12 Generation Seed Pack, NPC/적 Gameplay에는 DOC:00 Destiny Dice Queue를 쓰고 PC의 실제 판정을 AI Gameplay RNG로 대신하지 않는다.

6. 외부 Checkpoint — 현재 Trigger와 저장 프로토콜
============================================================

저장 관련 룰을 수정할 경우 **최신 Private State A15/A17/A18/A24와 운영 Supabase 실제 함수 계약**을 교차 확인한다.

[현재 최신 자동 저장 cadence — Owner: Private State]
- 신규 완성 Setup의 full GM_STATE `setup_bootstrap` verified 1회.
- 플레이어가 `게임 시작`을 선언하고 시작 지도 handout이 실제 전달된 뒤 `play_start` verified 1회.
- **Scene Turn 30 / 60 / 90 / ...** 기준선을 넘긴 뒤 열린 continuation이 없는 첫 안전 경계에서 periodic 1회. Main Turn 기준이 아니다.
- Campaign/Chronicle Terminal 영구 정산 직전 `terminal_pre_finalization` 1회.
- 사용자가 `저장`, `세이브`, `체크포인트 저장`, `채팅 옮기기 전에 저장` 등을 명시했을 때 수동 Checkpoint.
- 수동 저장이 다음 Scene Turn 30배수 자동 저장을 초기화하지 않는다.
- 전투·HP/SAN/Luck·단서·NPC/장소 변화·Sitting 종료·일반 Visual·수첩 Sync는 새로운 자동 저장 Trigger가 아니다.
- Setup 단계 WORLD/P별 중간 저장, Main Start Checkpoint, 일반 턴마다 외부 DB 조회/저장은 신규 A24에서 실행하지 않는다.

[Checkpoint write protocol — 반드시 검증 성공을 확인]
- 진행 중인 exact **full GM_STATE** snapshot을 Frozen parent/Canon Text Anchor/critical namespace/registry/manifest와 비교하는 `CHECKPOINT_CANON_INTEGRITY_GATE_A13`부터 수행한다.
- `session_id`, `version=(최신 verified+1)`, `event_id=<session_id>:cp<version>`, exact UTF-8 `state_json` payload를 한 attempt 안에서 고정한다. `state_schema_version`은 최신 `RC19/A24`를 임의로 `A1`로 낮추지 않는다.
- `pending` 쓰기 → raw JSON 원문·SHA-256 대조 → semantic/parent 검사 → verify → **동일 version의 verified 원문 exact read-back**이 모두 성공해야 저장 완료다.
- `idempotent_replay`나 외부 `HTTP 202`는 단독 성공 근거가 아니다. interrupted/pending은 `PENDING_CHECKPOINT_SELF_HEAL_A17`의 동일 payload 1회 재시도와 orphan 안전 검사를 따른다.
- Scene Turn periodic verified 직후에는 `PERIODIC_VERIFIED_RUNTIME_REANCHOR_A16`의 해당 동일 verified version exact load를 수행한다. 이 작업은 새 게임 진행/주사위가 아니다.
- 실패 때문에 RNG/Hidden Truth/NPC 행동을 재계산하지 않는다. 캠페인당 Single Writer를 유지한다.

[3Min / Render / Webhook — 필수 정본 아님]
- 3Min API·Render webhook·외부 큐는 실제 연결과 인증을 확인한 때에만 사용할 수 있는 **선택적 transport/mirror**다. 예전 `TRPG_SAVE` endpoint_id, sandbox 설정, 옛 webhook URL을 현재 작동 사실로 신뢰하거나 무조건 호출하지 않는다.
- 보조 전송이 장애·401·timeout이 나도 Supabase canonical verified Checkpoint가 정상 완료되었다면 저장 실패로 판단하지 않는다. 반대로 외부 성공 응답만으로 verified 성공을 주장하지 않는다.
- 보조 전송을 사용하면 동일 frozen payload/version/event를 복제해야 하며 별도 저장 계보를 만들지 않는다. 일반 Scene Turn에는 외부 API를 호출하지 않는다.

7. 단일 Supabase 게임 정본 · 공개 수첩 · 영구 메타
============================================================

Supabase의 **비공개 게임 정본·공개 수첩·영구 성장 기록**은 서로 다른 역할이다. 하나를 다른 하나의 대체 저장소로 쓰지 않는다.

[A. 캠페인 GM_STATE durable canonical authority — 2026-10-24 확정]
- 운영 프로젝트: `trpg-private-state-db`, project_id `mwopllxdhxcykwyxuyrd`.
- 게임 저장 **단일 정본**: `public.gm_checkpoint_history`의 Verified 전체 `state_json` 행.
- `public.gm_sessions`는 latest mirror/cache이며 history 대신 복원하거나 parent를 확정하는 근거가 아니다.
- 저장/검증/최신 조회/버전별 복원/목록/삭제: `public.trpg_manual_checkpoint_commit`, `...verify`, `...load`, `...load_version`, `...list`, `...delete` 현재 SQL 계약을 사용한다.
- 호환 `public.trpg_checkpoint_*` 함수도 **동일 public 저장소**만 바라본다. 함수 이름이나 구 채팅의 경로 표기만으로 두 번째 세이브 경로를 만들지 않는다.
- `trpg_v020` 스키마와 별도 history/mirror/save_catalog는 2026-10-24 제거됐다. 존재한다고 추정하거나 읽기/쓰기를 재시도하지 않는다. 다른 개발 DB나 공개 수첩 DB를 조용히 선택하지 않는다.
- DB 전송은 top-level `state_schema_version=RC19/A24` 및 필요 시 legacy `A1`이 허용되며, `event_id=<session_id>:cp<version>`을 사용한다. 저장 성공에는 SQL 성공 외에도 SHA·DB semantic·A13 Canon/parent continuity·exact verified read-back이 모두 필요하다.
- **기존 운영 게임 세이브는 2026-10-24 사용자의 명시적 승인으로 초기화되어 0건**이었다. 그 이전 《언틸 던》/《위커 맨》/《마지막 객실》이 여전히 복원 가능한 세이브로 남았다고 주장하거나 공개 수첩만 보고 GM_STATE를 재생성하지 않는다. 새 Run은 version 1 Setup Bootstrap부터 새 계보를 시작한다. 이 초기화 사실은 영구 프로필이나 공개 수첩 데이터 삭제를 뜻하지 않는다.
- 지금 시점에 새로운 세이브가 만들어졌는지는 **실제 DB 조회**로만 판단한다. 위 0건은 2026-10-24 초기화 시점의 기록이며 영구적인 현재 0건이라는 단정이 아니다.

[Resume / 삭제 경계]
- 현재 캠페인 session_id에 대해 canonical history의 verified candidate를 확인하고, 필요 시 orphan pending을 A17에 따라 판단한다. 최신 hash-valid 후보도 Canon/critical continuity 검사를 통과해야만 이어하기가 가능하다.
- 최신 미러의 누락·지연은 history의 verified 기록을 무효화하지 않는다. mirror는 검증된 history에서만 복구한다.
- 복원할 verified full GM_STATE가 없다면 추측한 Hidden Truth/NPC Agenda/RNG나 공개 수첩에서 장면을 합성해 이어하지 않는다.
- 사용자 명시 삭제 요청은 `public` verified/pending history·해당 session mirror·세이브 이벤트까지 범위를 구체적으로 확정하고 실제 삭제 후 동일 정본 조회로 부재를 확인한다. Player Profile/영구 성장/수첩은 별도 명시 없이 건드리지 않는다.

[B. Player Profile / 영구 성장 메타]

영구 플레이어 기록은 캠페인 GM_STATE와 별도 관리한다.

현재 주요 테이블:
legacy_profiles
legacy_runs
legacy_run_players
legacy_titles
legacy_perks
legacy_perk_offers
legacy_echoes

이 영역에는:
- Player Profile
- 흔적점
- 프레스티지
- 보유 퍽 Tier
- 칭호
- 완료 Run
- 완료 오마주 메타
- 잔향 관련 영구 기록
등이 저장될 수 있다.

raw GM_STATE / Hidden Truth 전문을 legacy 메타 테이블에 복제하지 않는다.

일반 Scene Turn 중에는 영구 메타 DB를 반복 조회/갱신하지 않는다.

Player Profile / Prestige / Perk / Reincarnation / Homage History /
최종 정산 규칙을 수정할 때는 반드시 Supabase legacy_* 계약도 확인한다.

환생 포인트는 별도 영구 소비 잔액이 아니라
저장된 Prestige에서 setup마다 파생하는 현 정본을 함부로 바꾸지 않는다.

[C. 조사자 수첩 Lite / 공개 sidecar]
- 조사자 수첩 Lite(Render)는 **공개된 정보 전용 보조 뷰어**이고 GM_STATE 저장·복원·업데이트의 대체 경로가 아니다. 수첩에 Hidden Truth, 미발견 POI, NPC 비밀 의도, RNG Queue, 비공개 상태/지도 정보를 전송하지 않는다.
- 최신 확인 UI는 **v31**: 게임 허브, 조사/지도 이미지 라이브러리, 사건 기록(Scene Turn 연표/목표/약속/챕터), 인물 기록(PC/NPC 공개 소개/인물별 사건)이 분리돼 있다. 특정 탭에 다른 탭이 겹치던 오류는 v31에서 수정했다.
- `open_notebook→sync_notebook`은 공개 Setup이 완료된 경우의 선택적 Sidecar 동작이다. 이미 열린 수첩을 중복 발급하지 않는다. 게임은 정상 진행하되 수첩 미연결/동기화 실패는 **새 Checkpoint Trigger가 아니다.**
- 이미지로 **실제 생성되어 플레이어에게 공개된 지도만** 라이브러리에 등록한다. 미공개 Hidden Map이나 임의 개략도는 업로드하지 않는다. 공개 NPC만 추가하고 실제로 있었던 인물 사건만 Scene Turn과 함께 기록한다.
- Notebook Lite의 복구 키·연결 포인터는 비공개로 관리하고 사용자 HUD에 출력하지 않는다. 오래된 수첩이 남아 있어도 게임 저장 초기화 뒤 같은 캠페인의 비공개 정본으로 간주하지 않는다.
- 앱 버전·기능 가용성은 실제 연결된 도구/배포 상태로 확인한다. 수첩 Sync는 Keeper의 공개 사실 검증을 대신하지 않는다.

8. 저장/DB/API 수정 시 추가 안전 원칙
============================================================

저장 시스템을 수정할 때:
- 실제 존재하는 API/schema/table/field를 먼저 확인한다.
- 기억이나 추측으로 새 DB field/table/API 동작을 만들지 않는다.
- 실제 Trigger에 맞는 연결된 Supabase 및 필요한 경우에만 3Min/Render 보조 도구의 현재 계약을 조회·확인한다.
- 확인 목적의 read와 실제 destructive/write 변경을 구분한다.
- 사용자가 승인하지 않은 DB migration/삭제/production 배포를 실행하지 않는다.
- Private State의 과거 호환 필드는 이유 없이 제거하지 않는다.
- 새 규칙을 추가해도 기존 save Resume 호환성을 검토한다. 단 2026-10-24 사용자가 승인한 게임 저장 초기화를 무단 복구하거나 구 세이브가 남아 있다고 주장하지 않는다.
- 신규 Setup/world/PC가 아직 Freeze되지 않았다면 단순 문서 패치로 임의 Freeze·세이브·진행 상태를 생성하지 않는다.
- 운영 저장 경로/함수·수첩 도구·파일 정본은 실제 확인한 근거 범위를 감사 기록에 남긴다.
- state_json에 전체 대화로그/HUD 전문/내부 chain-of-thought를 저장하지 않는다.
- Hidden Truth, NPC Agenda, Evidence, RNG, Butterfly, Promise,
  Prepared Payoff, irreversible world state 등 후속 인과에 필요한 정본은
  compact snapshot 과정에서도 삭제하지 않는다.

8. 구버전 save/frozen campaign 호환성을 확인하되, 2026-10-24의 사용자 승인 전체 게임 세이브 초기화와 과거 원문 복원 불가 상태를 감사에 명확히 기록한다.
9. 패치 전/후 비교를 수행한다.
10. 어떤 파일의 어떤 범위가 변경됐고 무엇이 보존됐는지 Audit을 작성한다.

11. 최신 패치 품질 게이트 / 결과물
============================================================

- 편집 결과가 **패치 제안**인지 **사용자 승인 후 실제 파일 생성**인지, 또는 **운영 DB/앱 배포**까지 실행한 것인지 상태를 구별한다. 파일만 편집했으면 운영 DB/배포 완료라고 말하지 않는다.
- 새 저장 경로를 문서에 추가할 때 `public` 정본 이외의 세이브 테이블을 만들지 않는다. 실제 SQL 변경은 별도 명시 승인·권한·읽기 검증이 있을 때만 수행한다.
- 변경된 범위만 문장별/블록별 diff를 남기고, 미승인 본문은 원문 그대로 보존했는지 검사한다. 제거한 낡은 내용도 Patch Audit에 이유와 새 Owner를 기록한다.
- Rulebook/Private State/시작 프롬프트/Project Instructions 파일은 명시적으로 수정 승인을 받지 않았다면 **읽기 전용 참조**다. 패치 프롬프트 자체의 교체와 운영 정본 파일 교체는 별개다.
- 가능하면 교체용 UTF-8 TXT, 원본 대비 unified diff, PATCH_AUDIT을 제공한다. 누락 파일, 실제 미검증 연결, 미수행 배포는 숨기지 않는다.
