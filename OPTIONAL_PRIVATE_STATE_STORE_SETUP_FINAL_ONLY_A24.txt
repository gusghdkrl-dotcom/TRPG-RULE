**Pre-write semantic check**
1. 저장 대상은 현재 working GM_STATE의 full snapshot이어야 하며 HUD/요약/최근 장면만으로 새 snapshot을 재구성하지 않는다.
2. `parent_verified_version`을 현재 최신 semantic-valid verified checkpoint로 고정하고 parent와 Critical namespace를 비교한다.
3. 같은 Scenario/Chapter의 Frozen root가 ordinary save 중 바뀌거나 사라지면 저장을 중단한다. 단 `periodic_scene_turn` pre-write에서 **단순 absent/null로 소실된 Frozen root**는 최신 semantic-valid verified parent에 동일 Scenario/Chapter의 exact 값이 있고 그 사이 승인된 Core 변경 기록이 없을 때만, Integrity Gate가 이미 읽은 parent payload를 재사용해 해당 namespace만 exact recovery overlay할 수 있다. 값이 서로 다르거나 변형된 경우에는 자동 덮어쓰지 않는다. 그 밖의 허용 예외는 명시적 새 Chronicle Chapter Freeze, 사용자 승인 recovery/migration, 또는 정본 규칙이 허용한 exact 구조 이동이며 그 event/ref를 남긴다.
4. Durable evolving namespace는 내용 변화가 가능하지만 **namespace 전체 소실**은 정상 해결로 취급하지 않는다. 모든 Agenda가 끝났다면 resolved/tombstone/ref를 남기고, Evidence가 소모돼도 획득/결론 정본을 삭제하지 않는다.
5. RC19 Canon Text Anchor는 구조화 정본의 손실 방지용 immutable exact anchor다. 정상 진행 중 구조화 Frozen root와 대응 anchor가 서로 다르면 어느 한쪽을 임의 승자로 정하거나 text에서 기계를 재구성하지 않고 `checkpoint_canon_recovery_required`로 멈춘다. evolving state를 text anchor로 stale backfill하지 않는다.
6. `checkpoint_canon_manifest{parent_verified_version, ruleset_version, state_schema_version, critical_namespaces{...}}`를 snapshot 안에 둔다. `critical_state_registry`의 실제 활성 항목을 manifest에 투영하며 각 critical entry는 최소 `present/status`를 기록하고, 구현이 deterministic canonical JSON digest를 지원하면 namespace SHA-256을 함께 기록한다. Manifest/Registry는 실제 namespace를 대체하지 않는다.
7. 위 검사를 통과하지 못하면 **새 version/event를 verified로 승격하지 않고 기존 verified pointer를 그대로 유지**한다. 실패 때문에 Hidden Truth/RNG/NPC 행동을 재생성하지 않는다.

**Write/read-back**
- 기존 `pending -> whole state SHA-256 -> read-back exact match -> verified` 절차에 semantic check를 추가한다. Hash 일치는 `같은 불완전한 snapshot을 잘 저장했다`는 뜻일 수 있으므로 semantic pass가 별도로 필요하다.
- `gm_checkpoint_history`/동등 verified history는 append-only로 취급한다. 새 checkpoint 작성은 과거 verified payload를 UPDATE/DELETE/대체하지 않는다. `gm_sessions` 같은 latest mirror/cache는 history를 대신하지 않는다.
- read-back 뒤 state hash뿐 아니라 `checkpoint_canon_manifest`, Critical namespace presence, parent link를 다시 검사한 뒤에만 최신 verified pointer를 이동한다.
</CHECKPOINT_CANON_INTEGRITY_GATE_A13>

<AUTOMATIC_CHECKPOINT_CADENCE_STATE_A15>
**Owner:** Private State Store. 신규/진행 캠페인의 자동·수동 Checkpoint는 기존 `gm_checkpoint_history.state_json` full snapshot + `gm_sessions.state_json` latest mirror 구조를 그대로 사용한다. DB table/schema migration은 요구하지 않는다. 실제 DB RPC 이름이 legacy `trpg_manual_checkpoint_*`이어도 payload/version/event 계약이 같으면 동일 verified commit 경로를 재사용할 수 있으며, `checkpoint_kind`는 state_json 내부 메타로 둔다.

**Trigger 종류**
1. `setup_bootstrap` — Scenario Core/Frozen root와 신규 scope의 scenario_progress_model/state, 전원 PC Final State(시작 Specialty 포함), Profile binding(ON일 때), Scenario Connection, 멀티 PC convergence, canonical/player map spec과 RC19-native Canon Anchor가 모두 semantic-complete가 되어 `setup_canon_complete=true`가 된 뒤 `awaiting_game_start`를 플레이 가능 상태로 열기 전 정확히 1회. 신규 session의 첫 verified version이어야 한다.
2. `play_start` — `game_started=true / phase=play / scene_turn=1` commit 뒤 start map handout이 delivered된 상태에서 첫 Play Scene 전에 정확히 1회.
3. `periodic_scene_turn` — nominal threshold `30,60,90...`을 넘긴 뒤 direct result와 열린 continuation이 모두 commit된 첫 안전 경계에서 1회.
4. `terminal_pre_finalization` — `CAMPAIGN_TERMINAL/CHRONICLE_TERMINAL`의 `ending_state.finalization_event_id`가 Freeze되고 열린 continuation이 없는 안전 경계에서 permanent settlement 시작 전 정확히 1회. `CHAPTER_TERMINAL`, Sitting 종료, 전투/SAN/Evidence/장소 이동/일반 Visual 자체에는 적용하지 않는다.
5. `manual` — 사용자가 명시적으로 요청할 때 언제든. 자동 cadence를 리셋하지 않는다.

**Cadence state**
- `checkpoint_cadence_state{bootstrap_status:pending|verified|failed, play_start_status:pending|verified|failed, terminal_pre_finalization_status?:pending|verified|failed, next_scene_turn:30, last_auto_scene_turn?, last_verified_version?, deferred_reason?}`를 durable GM_STATE로 둔다.
- setup/play-start가 이미 verified면 같은 명령 재입력로 새 checkpoint를 반복 생성하지 않는다.
- Scene Turn이 Ellipsis 등으로 여러 threshold를 건너면 현재 full state를 동일하게 30/60용으로 복제 저장하지 않고 안전 경계에서 1회 저장한 뒤 `next_scene_turn`을 현재보다 큰 다음 30배수로 전진한다.
- threshold가 열린 Combat/Chase/Roll/Luck/Bout/Handoff/Reaction/Visual/장기행동 continuation 중이면 `deferred_reason`만 두고 그 흐름을 먼저 정확히 끝낸다. autosave 때문에 공격/판정/선택을 끊지 않는다.

**Commit/verification**
- 모든 종류는 `CHECKPOINT_CANON_INTEGRITY_GATE_A13 -> pending write -> exact SHA-256/read-back -> semantic/manifest/parent recheck -> verified` 순서가 동일하다.
- version은 checkpoint 종류와 무관하게 최신 verified +1, `event_id`는 현재 DB 계약에 맞춰 `session_id:cp{version}`을 사용한다. kind/trigger reason은 state_json의 `checkpoint_kind`/cadence state로 구분한다.
- pre-write semantic pass 뒤 실제 DB write가 시작되면 그 Checkpoint attempt의 `version + event_id + exact state_json payload`는 verified 또는 명시적 recovery 전까지 불변이다. write/verify 중단을 이유로 새 version/event를 만들거나 더 최신 working state를 같은 attempt의 payload로 바꿔치기하지 않는다.
- pending write 뒤 verify/read-back이 도구·네트워크·응답 중단으로 완결되지 않았거나 동일 payload 재전송이 `idempotent_replay`로 확인되면, Private State `PENDING_CHECKPOINT_SELF_HEAL_A17`을 먼저 적용한다. 정상 Self-Heal이 가능한 동안 이를 새 저장 실패나 새 Checkpoint로 취급하지 않는다.
- 자동 저장 자체는 Timeline/Scene Turn/RNG/World/NPC/HP/SAN/Luck/Inventory를 진행하지 않는다.
- setup_bootstrap 또는 play_start가 Self-Heal까지 실패하면 정상 Play 시작을 허용하지 않는다. periodic이 Self-Heal까지 실패하면 현재 working state는 보존하되 다음 독립 Play commit 전에 `checkpoint_write_required` 또는 semantic recovery 상태로 멈춘다. 실패를 이유로 Hidden Truth/NPC Agenda/Evidence/RNG를 재생성하지 않는다.
</AUTOMATIC_CHECKPOINT_CADENCE_STATE_A15>

<SYSTEM_LOCK: VERIFIED_STORAGE_TRANSPORT_AUTHORITY_A18>
목적: Checkpoint의 **durable canonical storage**와 외부 전송/미러 계층을 분리하여, 3Min/Render/Webhook 같은 보조 경로의 지연·인증·endpoint 변경이 정상 저장·Resume·Runtime Re-anchor를 막거나 이중 version lineage를 만들지 않게 한다.

- 신규/진행 캠페인의 durable Checkpoint 정본은 Supabase/PostgreSQL의 append-only `gm_checkpoint_history` verified row다. `gm_sessions`는 최신 verified state의 mirror/cache이며 history를 대체하지 않는다.
- `AUTOMATIC_CHECKPOINT_CADENCE_STATE_A15`, `PENDING_CHECKPOINT_SELF_HEAL_A17`, `PERIODIC_VERIFIED_RUNTIME_REANCHOR_A16`, Resume parent 선택은 모두 **direct verified history commit/verify/load 경로**만으로 성공/실패를 판정한다.
- 3Min API, Render webhook, 기타 queue/transport/cache는 설정되어 있을 때만 사용할 수 있는 **optional external transport/mirror**다. endpoint 부재, connector 미연결, timeout, 401/403, retry exhausted, webhook 장애, endpoint ID 변경은 direct verified history Checkpoint가 정상 완료된 경우 저장 실패나 recovery 상태의 원인이 아니다.
- 반대로 외부 transport가 HTTP 202/record success/delivery success를 반환했더라도 동일 `session_id/version/event_id/state_json`이 canonical verified history에 verified되지 않았다면 정상 Checkpoint로 취급하지 않는다. 외부 mirror는 verified pointer나 parent를 결정하지 않는다.
- optional transport를 사용할 경우 Maintenance/Setup에서 실제 endpoint와 인증 설정을 현재 연결 상태로 발견·검증한다. prompt, legacy save, 오래된 문서에 기록된 endpoint ID를 런타임 사실로 신뢰하지 않는다. Ordinary Play 중 endpoint 생성·재구성·credential 교체를 자동 시도하지 않는다.
- optional transport로 보내는 payload는 해당 Checkpoint attempt에서 이미 Freeze된 exact payload를 재사용하며 transport가 version/event/state_json을 수정하거나 별도 lineage를 만들지 않는다. 외부 mirror 실패 때문에 Hidden Truth/NPC Agenda/Evidence/RNG를 재계산하거나 새 Checkpoint를 만들지 않는다.
- direct verified Checkpoint 성공 + optional mirror 실패인 경우 필요하면 `checkpoint_transport_warning{transport,reason,last_attempt?}` 같은 비정본 진단 상태만 둘 수 있다. 이 warning은 Play, Resume, Re-anchor를 차단하지 않으며 다음 canonical checkpoint cadence를 리셋하지 않는다.
- Resume은 canonical verified history를 우선한다. legacy 3Min-only/외부-only snapshot은 direct history가 없을 때 자동 정본 승격하지 않고, 사용자가 명시한 migration/recovery에서 hash·semantic continuity를 검증한 뒤 새 canonical history로 가져올 수 있다.
</SYSTEM_LOCK: VERIFIED_STORAGE_TRANSPORT_AUTHORITY_A18>

<SYSTEM_LOCK: PENDING_CHECKPOINT_SELF_HEAL_A17>
목적: `pending write`는 성공했지만 verify/read-back 호출이 중단되어 append-only history에 **미검증 pending만 남는 상황**을, 새 저장본 생성이나 게임 진행 없이 동일 Checkpoint attempt로 안전하게 완결한다.

- Checkpoint attempt는 pre-write semantic pass 직후 `session_id / version / event_id / exact state_json payload`가 Freeze된다. pending/verify가 끝나기 전에는 Timeline/Scene Turn/RNG/World/NPC/PC state를 추가 진행하지 않으며, 재시도용 payload를 현재 대화 요약이나 더 최신 working state에서 다시 직렬화하지 않는다.
- 정상 경로에서 `commit`이 `stored_new`, `stored_update`, 또는 동등한 pending 저장 성공을 반환하면 즉시 같은 exact payload로 verify를 수행한다. `commit`이 **동일 version/event/payload/hash에 대한 `idempotent_replay`**를 반환하면 중복 저장 실패가 아니라 `이미 같은 pending/verified attempt가 존재함`으로 해석하고 같은 verify 단계로 이어간다.
- verify 호출이 timeout/도구 중단/응답 유실 등으로 terminal 결과를 주지 못한 경우, 같은 `version + event_id + exact state_json`으로 **자동 재시도 최대 1회**를 허용한다. 필요하면 commit을 같은 tuple로 1회 replay한 뒤 verify한다. 이 재시도는 새 version/event를 만들지 않고 cadence도 전진시키지 않는다.
- 응답 중단이나 새 채팅 진입 뒤 **orphan pending**이 발견되면 pending을 정본으로 바로 승격하지 않는다. 먼저 append-only history의 해당 row가 (a) 최신 verified +1 또는 verified가 전혀 없는 신규 session의 version 1, (b) `event_id=session_id:cp{version}`, (c) 저장된 `state_hash`와 저장된 `state_json`의 exact SHA-256 일치, (d) `CHECKPOINT_CANON_INTEGRITY_GATE_A13`의 semantic/manifest/parent continuity 통과를 모두 만족하는지 검사한다.
- 위 조건을 모두 만족하는 orphan pending은 **그 DB row에 이미 저장된 exact `state_json` 자체**를 verify 입력으로 사용해 기존 verify 경로를 1회 완결할 수 있다. 대화 로그나 현재 working memory에서 Hidden Truth/NPC Agenda/Evidence/RNG를 재구성하지 않는다. verified 승격 성공 뒤에는 cadence/status를 정상 완료 처리하며, periodic 종류였다면 같은 version으로 `PERIODIC_VERIFIED_RUNTIME_REANCHOR_A16`을 이어서 실행한다.
- 다음 중 하나면 자동 승격하지 않는다: 동일 session에 해석 불가능한 복수 pending, version gap/역행, event/payload conflict, hash mismatch, semantic-critical namespace 손실, parent 불일치, 이미 다른 payload가 같은 event/version을 차지함. 이 경우 기존 verified pointer와 현재 working state를 보존하고 `checkpoint_write_recovery_required{session_id, version?, event_id?, reason}`로 멈춘다.
- 충돌 pending을 편의상 자동 `discard_pending`하거나 과거 verified 값으로 덮어쓰지 않는다. `discard_pending`은 해당 row가 미검증 orphan이며 보존 가치가 없다는 exact recovery 판단이 끝난 뒤에만 별도 repair 절차에서 사용할 수 있다.
- pending row는 verify 전까지 정상 Resume 정본이 아니다. `gm_sessions` latest mirror/cache가 pending보다 오래되거나 비어 있어도 history의 pending을 조용히 verified처럼 사용하지 않는다.
- 이 Self-Heal은 기존 `gm_checkpoint_history` append-only row 조회 경로와 `trpg_manual_checkpoint_commit / verify / load(_version)` 또는 동등한 현재 계약을 재사용한다. orphan pending 검사는 history의 저장된 row를 read-only로 확인하는 것이며 신규 DB table/schema migration을 요구하지 않는다.
</SYSTEM_LOCK: PENDING_CHECKPOINT_SELF_HEAL_A17>

<SYSTEM_LOCK: PERIODIC_VERIFIED_RUNTIME_REANCHOR_A16>
목적: 긴 동일 채팅에서 working context가 누적되며 Frozen/비공개 정본이 흐려지는 위험을 줄이기 위해, 기존 Scene Turn 30배수 periodic Checkpoint를 **저장 지점이자 런타임 정본 재정착 지점**으로 사용한다. 자동 저장 cadence 자체는 늘리지 않는다.

- 새 periodic version이 verified되면 **그 동일 `session_id + version + event_id`의 append-only verified history를 exact-version load**한다. `gm_sessions` 같은 latest mirror/cache는 Re-anchor source로 사용하지 않는다. legacy RPC 이름이 `trpg_manual_checkpoint_load_version`이거나 동등 기능이어도 무방하다.
- exact-version load 결과의 version/event/hash/state_json과 `checkpoint_canon_manifest`/Critical namespace를 다시 확인한 뒤에만 `working GM_STATE := loaded verified full state_json`으로 재정착한다. 이는 rollback이나 새 게임 이벤트가 아니라 동일 snapshot의 런타임 기준점 교체다. Timeline/Scene Turn/RNG/World/NPC/HP/SAN/Luck/Inventory를 추가 진행·재계산하지 않는다.
- Re-anchor를 위해 checkpoint를 한 번 더 쓰지 않는다. 저장 성공 뒤 **verified load 1회만 추가**하며, 전체 대화 transcript나 HUD를 다시 주입하지 않고 full GM_STATE만 사용한다. RC19 Canon Anchor/Registry도 이 exact full state 안에 포함되므로 별도 Canon DB fetch를 추가하지 않는다. RC20 Narrative Archive flush가 필요하면 이 Re-anchor가 완결된 **뒤에만** 시도한다. 플레이어 화면에는 정상 성공을 별도 출력하지 않는다.
- exact-version load 또는 재검증이 실패하면 이미 verified된 checkpoint 자체를 폐기하거나 과거 parent와 current state를 임의 병합하지 않는다. 현재 working state를 그대로 보존하고 `checkpoint_canon_recovery_required`에 `periodic_reanchor_load_failed` 사유를 두어 다음 독립 Play commit 전에 동일 verified version exact load를 재시도한다. 실패를 이유로 Hidden Truth/NPC Agenda/Evidence/RNG를 생성·재굴림하지 않는다.

<RESUME_CANON_RECOVERY_GATE_A13>

- 정상 binding은 최신 full GM_STATE snapshot의 일부로 `state_json`에 포함한다. 별도 DB column/table을 요구하지 않는다.

**Resume preflight**
- verified snapshot read-back 뒤 Play/Setup/settlement를 재개하기 전에 binding integrity를 검사한다.
- legacy snapshot에 필드가 없으면 같은 campaign의 검증 snapshot/확정 Setup 기록에서 exact P↔Profile mapping이 있는 경우에만 working state로 1회 normalize한다. 과거 snapshot 자체는 수정·재해시하지 않는다.
- exact 근거가 없으면 `profile_binding_recovery_required{slots[], reason}`를 working recovery state로 둘 수 있다. 이 상태에서는 Play 진행과 permanent finalization commit을 막고, 사용자에게 기존 Player Profile의 `profile_code` 또는 Lobby 선택 확인을 요청한다.
- 사용자가 아직 finalization되지 않은 legacy 캠페인에서 자신이 사용한 기존 Profile을 명시적으로 확인하면 `binding_source=user_repair_confirmation`으로 binding을 확정할 수 있다. 이는 PC 세계 상태를 바꾸지 않는다.
- 과거 qualifying Sitting/보상 귀속은 별도 확정 기록이 있을 때만 복구한다. binding을 고쳤다는 이유만으로 과거 Sitting 수나 보상을 추정 생성하지 않는다.

**Finalization preflight**
- 영구 성장 ON + 실제 참가 occupied slot가 하나 이상이면 confirmed binding 없이 `players=[]` 또는 일부 누락 players payload를 정상 finalization payload로 만들지 않는다.
- binding 오류 시 terminal 결과/ending state는 보존하되 settlement는 pending recovery로 유지한다. 같은 `finalization_event_id`를 재사용해 exact settlement를 이어가며 새 terminal 결과를 만들지 않는다.
- 이미 과거에 binding 없이 completed된 finalization은 자동 수정하지 않는다. 별도 repair 절차 없이 `legacy_profiles/legacy_runs/legacy_run_players`를 소급 갱신하지 않는다.

**Storage contract**
- Supabase `gm_sessions.state_json` / `gm_checkpoint_history.state_json`은 text snapshot이므로 이 binding field 추가만으로 DB schema migration을 요구하지 않는다.
- Player Profile 본체는 기존 `legacy_profiles.player_key/profile_code`가 정본이며 GM_STATE에는 연결 ref만 둔다.

- 문학적 확장은 HUD/주사위/기계 표현을 자연어 사건으로 바꾸고, 이미 확립된 시대·장소·시각 Canon의 비인과적 감각 묘사와 장면 전환을 풍부하게 하는 데 사용할 수 있다. 그러나 발생하지 않은 행동/대사/단서/인과를 만들거나 PC의 미선언 내면·감정·추리·윤리 판단을 창작하지 않는다. 실제 대사는 의미·의도를 유지하는 범위에서 문장부호/호흡만 다듬을 수 있다.
- 원고는 source density에 맞춰 장면 중심으로 충분히 길게 전개하되, 분량 목표 때문에 새 사건을 발명하지 않는다. 반복적인 이동/탐색은 압축할 수 있고 핵심 대화·공포·실패·선택·발견은 충분히 dramatize한다.
- `scene_visibility.authorized_player_slots/transmission_scope`를 source projection에 보존한다. Final Novel은 해당 Run의 실제 공유/전달 범위를 넘어 Hidden Truth를 사후 해설하지 않는다. 미발견 진실이 남아 있는 Ending이면 소설에도 그 불확실성이 남을 수 있다.
- 소설 문장/편집 결과는 gameplay state로 역수입하지 않는다. Archive가 더 그럴듯해 보여도 Evidence/Hidden Truth/NPC Agenda/PC state를 수정할 권한이 없다.
- finalized campaign에서 gameplay Resume은 계속 금지하되, Novel/Legacy Archive가 미완료면 `POST_RUN_ARCHIVE_RESUME`로 마지막 완료 cursor/revision부터 후처리만 이어갈 수 있다.
