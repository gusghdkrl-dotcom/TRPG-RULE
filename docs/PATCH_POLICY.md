# 패치 규정

이 문서는 TRPG-RULE 저장소의 **매 패치 공통 준수 기준**이다. 수정 전에 전체를 읽고, 완료 전에 실제 변경 범위에 해당하는 항목을 다시 대조한다. 사용자 요청과 대화에서 이미 확정한 결정·승인 범위를 우선한다. 분석 요청은 적용 승인과 구별하고, 승인된 패치는 수정·검증·기록·GitHub 반영까지 마친다.

[AGENTS.md](../AGENTS.md)는 필수 참조 진입점, 이 문서는 공통 규정, [EDITING.md](EDITING.md)는 파일별 배치와 편집·검증의 상세 절차다. 과거 브랜치·DEVLOG·설계 초안은 이력이며 최신 원문을 대신하지 않는다. 이 규정은 개발 작업용으로, 게임용 프로젝트 인스트럭션이나 배포 ZIP에 추가하지 않는다.

## 1. 최신 기준과 실제 문제 확인

- GitHub `main`의 실제 최신 HEAD와 작업 트리의 기준 커밋을 확인한다. 오래된 로컬 파일로 최근 패치를 덮어쓰지 않는다.
- 사용자가 관측한 문제·발생 조건과 추정 원인을 구별한다. 현재 규칙/생성물·입력/상태·실제 도구 지원을 확인해 수정할 동작을 정한다.
- 우선순위는 **PC 주도권·공개 범위·확정 사실/저장 보호 → 실제 플레이 장애 해결 → 일관된 규칙 실행 → 원작 체험 → 출력 편의**다. 기존 기능·묘사·NPC 자율성·게임 경험을 편의 때문에 없애지 않는다.
- 규칙 추가 자체, 새 검증 체계·앱·서버 구축을 목표로 바꾸지 않는다. 불명확한 과거·미정 정책·지원하지 않는 기능을 확정 사실처럼 메우지 않는다.

## 2. 수정·추가·삭제와 충돌 정리

1. 변경 개념/기존 표현을 **전체 실행 소스에서 검색**하고 담당 원문·직접 호출부·예외·색인·템플릿의 영향 범위를 찾는다. 매 패치 전180개 규칙을 다시 분류할 필요는 없지만 담당 절 하나만 보고 끝내지 않는다.
2. 원인을 가진 본문을 수정하고 새 동작과 **충돌·상반·중복되는 기존 문구**를 같은 패치에서 통합/수정/삭제한다. 새 Override·예외 문단을 쌓아 옛 지시를 덮지 않는다.
3. 삭제/통합한 기능을 여전히 호출하는 메뉴·선택지·ID·예전 수치·참조·검증 문구와 도달 불가능한 분기도 정리한다. 유효한 기능·예외·저장 호환을 검사 통과를 위해 지우지 않는다.
4. 역사 자료는 필요하면 구판 표시 후 현재 실행 경로에서 분리한다. 실제 과거 원문/해시·확정 결과를 고쳐 이력까지 맞추지 않는다.

## 3. 담당 문서와 템플릿 동기화

| 대상 | 담당 범위와 패치 기준 |
|---|---|
| `PROJECT_INSTRUCTIONS.md` | 진행 중 판단할 필수 행동 원칙·발동 게이트·짧은 담당 참조를 압축한다. 세부 수치·공식·효과 전문·생성/DB 명세는 담당 원문에 둔다. 조건부여도 발동하면 필수이며 조건·예외·공개 범위를 누락하지 않는다. |
| `START_GAME.md`·`rules/04-setup.md` | 설정·PC/세계 생성·시작 절차와 설계/완료 대조를 소유한다. 생성 시 검토를 게임 매 판정의 재검토로 바꾸지 않는다. |
| 담당 `rules/*.md` | 기능의 조건·절차·수치·예외·실패/재개 경계를 한 곳에서 정의하고 실제 연결된 호출부/색인도 맞춘다. |
| `templates/PRIVATE_CANON_TEMPLATE.md` | 생성·정본 필수 내용/절·준비 수치·검토 경로·저장 연결이 달라지면 담당 룰북과 함께 대조·수정한다. 공통 규칙 전문이나 별도 권위를 만들지 않는다. 영향 없는 폼을 형식적으로 바꾸지 않는다. |
| 저장/본부/카드·자산/배포 | 관련 문서·실제 계약·연결 지점만 함께 맞춘다. 문서 지시만으로 기능 구현·전달/저장 성공을 주장하지 않는다. |

프로젝트용 `PROJECT_INSTRUCTIONS.md`와 `START_GAME.md`는 **각각 공백·줄바꿈 포함7,800자 이하**로 계산한다. 상한을 채우려고 지시를 늘리지 않는다. 압축 전후 조건/기능 보존의 구체 대조는 [EDITING.md](EDITING.md)를 따른다.

설계 변경은 ‘충분히 준비한다’는 선언만으로 끝내지 않는다. 실제 값·대상·조건·수량/소유·시점·정식 ref와 결과별 경로가 정본 초안/상태에 있는지 확인한다. 예를 들어 위협·회복 변경은 [HARM_ECOLOGY](../rules/04-setup.md#harm_ecology)의 실제 참가자 자원·중간 회복·위협 경로를 대조한다. 설명용 예시/가상 경로를 고정 배수·피해 할당량·실제 플레이로 바꾸지 않는다. 세부 수치/합격 기준은 담당 룰북이 소유한다.

## 4. 기존 게임·세이브와 공개 범위 보호

- 신규 생성/독립 테스트와 재개를 구별한다. **기존 게임도 이후 미처리 단계는 현재 프로젝트 소스의 최신 룰북**으로 진행한다. 구판 룰북 보유를 재개 조건으로 요구하지 않는다.
- 확정 사건·수치/최대치·소유/소모·관계/개별 지식·안전/손실·현재 위치/시각·열린 입력·난수·생사/종결을 보존한다. 규칙 갱신만으로 세계/PC를 재생성하거나 치료·피해·보상을 소급 실행하지 않는다.
- 승인된 미공개·미발생 리뉴얼은 보존할 사실과 바꿀 준비를 먼저 나눈다. 새 정본/체크포인트로 연결하고 구판 원문·해시는 이력으로 남긴다. 가상 검토 결과를 실제 경험으로 저장하지 않는다.
- 저장/로드·누적 스토리·본부 연결은 [07-state](../rules/07-state.md)의 현재 계약을 따른다. 실제 저장/검증·파일 전달·프로젝트 업로드 성공을 구별하고 수행한 검증 범위까지만 완료를 보고한다.
- 실제 비공개 정본·세이브·인증정보를 공개 저장소/공통 ZIP에 넣거나 운영 DB·함수·권한을 임의 변경하지 않는다. 이미 승인된 범위는 계승하되 새로운 공개/외부 전송·파괴적 변경에 필요한 승인을 임의 추정하지 않는다.

## 5. 검증과 속도·품질 판단

- 변경에 필요한 최소 범위로 검증한다. 관련 성공 사례/실패 반례와 기존 검사를 먼저 사용한다. 매 패치 전체 회귀·새 테스트 엔진·무관한 DB/보안 검증을 의무화하지 않는다.
- 실행 소스·작성 폼·승인 자산/빌드가 바뀌면 `python3 scripts/rulebook.py check`를 수행한다. 구조 검사 통과는 의미/수치 적합성·실제 AI 플레이·외부 저장 성공의 증명이 아니다. 필요 시 관련 기존 회귀를 선택 실행한다.
- 실패가 실제 기능 결함인지 폐기 문구에 묶인 앵커인지 먼저 확인한다. 정당한 기능은 보호하고 낡은 앵커만 최소 갱신한다. 필요한 검사를 삭제하거나 미실행 검사를 통과했다고 보고하지 않는다.
- 속도 문제는 **모델 추론·서비스 지연·문맥/조회·도구 실행·저장 경계**를 구별해 관측 근거로 좁힌다. 증거 없이 특정 설정/룰북을 원인으로 단정하지 않는다. 글자 수·도구 수·사고 설정 변화만으로 같은 게임 경험/규칙 준수나 특정 응답 시간을 보장하지 않는다.
- 정적 검사·가상 경로/수치 검토·실제 서버 왕복·실전 AI 진행·응답 시간 실측을 구별해 기록한다. 실측하지 않은 속도 개선과 플레이하지 않은 품질은 미검증으로 남긴다.

## 6. 배포와 완료 보고

- 게임용 소스·템플릿·승인 자산/ZIP 생성 로직이 바뀌면 `check` 뒤 `python3 scripts/rulebook.py export`를 실행한다. 가능한 한 소스/폼과 `dist/TRPG-RULE-project.zip`을 같은 커밋에 넣고 ZIP 실제 원문·`RULESET.json`/`RULESET.md`·SHA256 manifest 일치를 확인한다. README 고정 다운로드 주소를 유지한다.
- 개발 지침·문서·DEVLOG만 바뀌고 배포 입력이 같으면 ZIP을 불필요하게 재생성하지 않는다. 기존 배포가 원문보다 뒤처져 있다면 그 사실을 이번 문서 변경으로 해결됐다고 표시하지 않는다.
- `DEVLOG.md`에 문제/원인·변경/영향·정리한 충돌/폐기 참조·보존 동작·검사 결과·미검증을 남긴다. 강제 푸시하지 않고 GitHub 최종 `main`과 실제 반영을 확인한다.
- CI는 무기한 대기 단계가 아니다. 필요 범위에서 확인하고 실패 시 실제 로그로 원인을 좁힌다. 상세 조회/재시도 범위는 [EDITING.md](EDITING.md)를 따른다.
- GitHub 수정이 기존 프로젝트 파일/채팅·진행 중 정본·세이브를 자동 교체하지 않는다. 완료 보고에 **바뀐 것·검증한 것·아직 적용되지 않은 것과 필요한 교체/로드 방법**을 구별한다.

## 매 패치 최종 대조

- [ ] 최신 `main`과 사용자 요청·승인 범위를 기준으로 작업했는가?
- [ ] 담당 본문/호출부·영향받는 폼을 맞추고 충돌·상반·중복·폐기 참조를 정리했는가?
- [ ] 기존 기능·게임 경험·확정 상태·공개 범위·현재 입력을 보존했는가?
- [ ] 관련 검증을 실제 실행하고 결과/한계를 기록했는가?
- [ ] 배포 입력이 바뀌었다면 소스·폼·ZIP/식별자/해시가 같은 결과물을 가리키는가?
- [ ] DEVLOG·GitHub 반영과 필요한 교체/재개 안내까지 완료했는가?

이 대조는 개발 패치의 완료 확인이다. 게임 매 턴 전수 검사·새 DB 원장·별도 승인 양식으로 실행하지 않는다.
