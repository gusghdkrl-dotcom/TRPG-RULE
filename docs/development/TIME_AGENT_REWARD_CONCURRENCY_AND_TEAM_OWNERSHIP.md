## 실제 개발 DB에서 성공한 검증

### 1. 열린 일반 드래프트 ↔ 연대기 특별 A 교차 순서

실행 SQL: `docs/sql/dev/tests/trpg_hq_phase10_cross_order_special_vs_draft_rollback.sql`

2인/3인 팀의 첫 검증된 연대기(챕터 2개)를 만든 다음, **원래 `trpg_hq.offer_general_reward / resolve_general_reward`와 `resolve_chronicle_special`를 실제 순서대로 실행**했다.

- **일반 먼저 제시 → 특별 A로 같은 카드 먼저 소유**: 현재 클래스 일반 드래프트의 첫 후보를 특별 A로 직접 받는 데 성공. 이후 첫 일반 슬롯 선택은 `card_already_owned_before_selection`으로 거부. 기존 일반 드래프트는 `offered` 상태 유지, 원래 적격한 두 번째 슬롯을 사용자가 선택하는 합성 입력으로 **정상 `resolved`**. 원 카드와 특별 카드는 각각 1장, 서로 다른 `acquisition_event`.
- **일반 먼저 수령 → 특별 A로 같은 카드 선택 시도**: 일반 드래프트 첫 카드 `resolved` 후, 그 카드를 특별 A로 중복 선택하면 `hq_special_card_already_owned`로 거부. 특별 훈장 `awaiting_choice` 보존, 다른 미보유 카드로 특별 A 선택 가능. 일반 지급 원장 훼손 없음.
- 2인과 3인 모두 **동일 호출 재실행 `applied:false`**, 별도 보상 원장 재조회 정합, 보상에 의한 NPC 개인 관계/클라라 질문 허위 생성 없음. 이후 별도 연대기 실패를 시뮬레이션해 과거 완주 훈장·일반 `resolved`·특별 `resolved` 보존.
- 실제 2인 회귀: 일반 보상 `resolved` 2건·특별 A 2건·첫 인증2/훈장2. 실제 3인: 각3건. **후속 실패 신규 훈장 0건**.
- 이 코드는 일반 드래프트의 네 후보를 DB 적격 풀에서 **결정론적으로** 선택한다. 실제 Python SystemRandom/09-cards 희귀도 추첨·실제 플레이어 선택은 아직 별도 통합 검증.

**정책 결론:** 열린 드래프트의 충돌한 슬롯을 자동 새 카드로 바꾸지 않는다. **기존의 유효한 다른 선택지를 플레이어가 직접 선택**하게 하며, 다른 후보도 없다면 그 미해결 상황을 별도 정책으로 정해야 한다. 이미 준 특별 A 카드를 회수하거나 일반 보상을 임의 몰수하지 않는다.

### 2. 같은 영구 UUID의 두 팀 소속·영구 카드/성장 공유

실행 SQL: `docs/sql/dev/tests/trpg_hq_phase10_cross_team_same_agent_rollback.sql`

**새로 확인한 기존 데이터베이스 보호 장치**: `hq_team_members`에는 `hq_one_active_team_per_agent` 고유 인덱스가 이미 존재하며, 동일 UUID가 **서로 다른 팀의 동시 활성 팀원**이 되는 시도를 거부한다. 이를 없애거나 우회하지 않았다.

검증용 단일 영구 UUID를 먼저 팀 1에 등록하고(훈련 자격은 가상 플래그), 2장의 V2 verified 정식 연대기를 완주·귀환·마틴 평가하여 **첫 인증·훈장1**을 부여한다. 이어 두 번째 팀에 **동시 활성 가입을 시도하면 고유 인덱스에서 거절**됨을 확인한다. 테스트용으로 첫 팀의 `left_at_minutes`를 직접 갱신해 명시적으로 소속 종료한 뒤 두 번째 팀의 또 다른 2장 연대기를 정상 완주한다. **이 SQL의 탈퇴 상태 갱신은 합성 픽스처 한정**이다. 실사용자의 팀 탈퇴·동의·새 팀 재입단 자동 처리를 구현한 것이 아니다.

테스트는 동일 UUID에 다음 세 가지를 각각 수행하며 모두 성공 후 롤백한다.

| 가상 후속 상황 | 검증 결과 |
|---|---|
| **두 팀의 훈장 A가 같은 카드 `GU-A-1`을 요구** | 첫 카드 1회만 소유. 다른 팀은 중복 소유가 거절돼 훈장 미선택 상태 보존, `GU-A-2`로 선택해 새 카드 정상 수령 |
| **두 팀의 훈장 B가 같은 `POW`에 확정 성장 +1을 각각 요구** | 실제 글로벌 성장 원장 `POW` 0→1→2. 각각 다른 정당한 훈장 선택권이므로 **합법적인 두 번의 성장**을 보장하되 한 훈장 재시도는 추가 증가0 |
| **기존 POW Lv.4이고 새 훈장 2개가 POW 성장 요구** | 첫 훈장으로 Lv.5 도달, 두 번째 POW 추가 증가 거부. 두 번째 훈장 선택권은 보존되고 다른 Lv.5 미만 항목 `STR` +1 정상 지급. 레벨 6 불가 |

- 새 임무 2개 완주로 훈장은 2개 생기지만 **첫 정식 시간요원 인증은 정확히 1건**, 원래 첫 인증 `mission_id` 유지.
- 팀별 훈장/이벤트는 분리돼 재조회 가능하고 영구 카드·성장 원장은 같은 `player_id`에 공유. 한 팀에서 카드 보유를 갱신한 뒤 **다른 팀의 revision 값이 바뀌지 않아도** 보상 RPC가 최신 전역 카드/성장 소유권을 다시 확인한다.
- 전부 **가상 요원·팀·정본·검증 저장·훈장·보상 자료**를 종료 전에 롤백.

### 3. 실제 동시 트랜잭션 검증의 한계

두 개의 Supabase SQL 연결로 **같은 본부 팀 행을 `FOR UPDATE` 하는 요청을 병렬 제출**했으나, 두 호출이 실제로 잠금 경합 중에 겹쳤다는 관측에 실패했다. 한쪽 쿼리는 정상 완료됐고, 다른 쿼리는 `concurrent_team_row_lock_was_not_observed`라는 시험 단언 실패를 반환했다. 따라서 이를 **서버 동시성 안전 검증 통과로 보고하지 않는다.**

이번 회귀에서 입증된 것은 **검증된 임무별 원장, 같은 영구 UUID의 두 역사적 팀에서의 순차·교차 보상 처리, 중복 보상·Lv.5 한도·활성 중복 가입 차단 및 롤백 정합**이다. 서로 다른 네트워크 연결에서 정확히 같은 순간 발행되는 **실제 A/B 카드/성장 지급 경쟁, row-level 대기·정확한 락 순서, 데드락 여부**는 별도 병렬 부하 검증이 남았다. 이 항목을 완료로 표시하지 않는다.

## 보안·주도권 및 기존 정본 경계

- 이미 운영 중인 `hq_one_active_team_per_agent` 제약은 유지한다. 다중 팀 소속을 허용하는 임의 정책 변경 금지.
- 과거 팀의 훈장 미선택 보상은 영구 UUID의 실제 획득 권리다. 팀 이동 과정에 선물처럼 보상/자격을 재생성하지 않는다.
- 합성 SQL의 팀 탈퇴/훈련/보상 선택은 **사용자가 실제로 동의하거나 실행한 행동이 아니다**. 실전에는 별도 PC/플레이어 입력, 권한 검증 및 실제 시간 변경이 필요하다.
- 미보유 카드 A, 성장 B, 일반 챕터 4후보 드래프트와 각각의 소유 원장은 별도. 실패·카드 중복/한도 에러 시 이미 실제로 받은 보상을 지우지 않는다.
- 운영 `main`과 운영 Supabase의 기존 세이브/카드/비공개 정본은 이 실험에 영향을 받지 않는다.
