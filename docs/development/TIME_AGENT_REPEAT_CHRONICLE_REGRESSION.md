# 시간요원 본부 8차 — 동일 정식 요원의 두 번째 완주·세 번째 실패 회귀 테스트

> DEV ONLY · 2026-11-12. 테스트 DB: `trpg-time-agent-dev` (`tvrfuljncwefbioasxgo`). GitHub `dev/time-agent-hq`. 운영 `main`·운영 Supabase 이식 없음. **원래 플레이어의 게임 행동이 아닌 합성 완주/실패 테스트**.

## 원래 계약

- 정식 시간요원 자격은 **첫 연대기 완주에서 영구 한 번**만 등록한다. 다른 연대기 완주가 첫 인증의 원래 `mission_id` 또는 `granted_at`을 바꾸지 않는다.
- 동일 요원의 **새 연대기 완주**는 그 임무에 대응하는 새 **영구 훈장 1개 및 특별 A/B 중 1개 선택권**을 부여한다. 첫 인증은 2회 발급하지 않고 임의 계급 점수/자동 승진도 없다.
- 추후 연대기 실패는 **그 실패한 임무에 대한 새 완주 훈장·보상만 막는다**. 기존 자격, 과거 훈장, 적법하게 받은 카드·영구 성장, 실제 PC의 생존/성과·정당한 이전 챕터 보상은 삭제하지 않는다.
- 플레이어가 직접 특별 A/B를 선택하기 전에는 어떤 보상도 자동 결정하지 않는다. 가상 테스트는 사용자 선택이 아니라 별도 테스트 입력이다.

## 검증 방법

실행 가능한 SQL: `docs/sql/dev/tests/trpg_hq_phase8_repeat_chronicle_rollback.sql`.

1. 개발 DB에 이미 존재하는 **완주·첫 정식 인증 1건 + 훈장 1개 + 첫 특별 카드 보상 1건이 있는 영구 UUID**와 그 기존 팀을 사용한다. 본래 인증 `first_mission_id`/`granted_at`, 훈장 키, 최초 특별 지급된 `RO-A-3` 카드의 `acquisition_event`, 기존 카드 총수/POW 성장·팀 revision/본부 시각을 기준선으로 조회한다.
2. 동일 UUID, **새 캠페인 ID**와 새 세션 ID를 만들어 두 번째 연대기 1장/2장을 원래 `trpg_v2_commit/verify` → `confirm_segment_terminal` → `return_segment` → `evaluate_segment` 흐름으로 실행한다. 첫 챕터는 `CHAPTER_TERMINAL completed`, 최종은 `CHRONICLE_TERMINAL completed`. 동일 가상 세계의 `parent_sha256`/버전을 이어 준다.
3. `approve_chronicle_completion` 실제 호출: `applied:true`, `medals:1`, `new_full_certifications:0` 확인. 같은 요청 재실행은 `applied:false`.
4. 새 훈장은 별도 `awaiting_choice`. `chronicle_special_options`로 후보 확인 후 **테스트용 가상 선택**인 특별 B `POW` 확정 +1 실행. 성장 DB 결과 이전보다 1 높은지 비교. 같은 B 선택 재실행 `applied:false`, 이후 다른 A 선택 시도 거부.
5. 동일 UUID·같은 팀으로 **세 번째 연대기**를 새로운 캠페인/세션으로 개설. 한 챕터를 verified `CHRONICLE_TERMINAL failed`로 종결·생존 귀환/마틴 평가 후 `mission.status=failed` 및 `approve_chronicle_completion` 거부 확인.
6. 이 실패 후 첫 정식 인증 **계속 1건**, 원래 `first_mission_id`/날짜 일치, 첫 훈장/기존 카드 지급 `acquisition_event` 불변, 두 번째 훈장/성장 B 유지, 세 번째 실패 임무 훈장 없음, `load_chronicle_honors` 과거 2건 모두 원장 일치 재확인.
7. 모든 테스트 작업을 **의도적으로 예외 처리하여 서브트랜잭션 롤백**. 바깥 임시 보고 테이블 결과 1행만 반환하고 테스트 종료 후 폐기. 실제 기존 개발 카드/성장·체크포인트·팀 본부 시간도 수정하지 않음.

## 결론과 결함 여부

**기존 6a/6b/6c, 7a/7b 실행 함수가 이 경로를 이미 올바르게 처리했다. 이번 8차에는 DB 스키마/함수 마이그레이션 수정이 필요하지 않았다.** 검증 가능한 SQL만 GitHub 개발 브랜치에 추가했다. 다른 실제 플레이어의 본부 기록/소유물에는 영향을 주지 않는다.
