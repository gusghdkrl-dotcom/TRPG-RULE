# 상태·저장·재개 흐름

신규/독립 재시험은 실제 최신 룰북·배포 ID와 새 campaign/session으로 설계→정본 초안/최초 STATE→그 작성물의 COMPATIBILITY_GATE→동일 원문 등록/첫 출력·저장 순서를 따른다. 재개는 기존 정본/verified 누적 상태를 보존한다. 룰북 수정으로 이전 캠페인을 자동 재생성하거나 DB 스키마를 바꾸지 않는다. 첫 위치/미실행 행동·NPC 위치/소유는 동일 초기 사실에서 투영하며 적의 추적/경비/배회 현재 위치·마지막 실제 정보·다음 행동/중단은 기존 동적 수납에 잇는다. 로컬 테스트 요약과 운영 checkpoint/서버 verified를 구별한다.


현행 실행 정본은 rules/07-state.md다. 2026-11-09부터 인증된 새 Supabase `trpg-state-v2` (project ref `taoaffdyssqtnjszumpq`)의 `public.gm_checkpoint_history` verified 원문을 사용한다. 서버 스키마는 `TRPG_STATE_V2`, 저장모드는 DOCUMENT_BOUND(DB1)이며, 개발/이전 검증기를 복사하지 않았다. 실제 설치 SQL은 [trpg-state-v2.sql](sql/trpg-state-v2.sql)이다.

1. 실제생성/로드한정본과누적상태에서현재작업범위를구성한다.
   신규 저장도 기존 V2/DB1 JSON 구조를 사용한다. `world_delta.drivers`는 일반 E의 실제 세계 변화, `story_context.main_track_by_pc`는 P슬롯별 E 참조/공개 가능 방향·체험·현재 별도 활동, `ongoing_consequences`는 물리 재난·HP0 구조/이송 과정, `pcs/runtime/scene_context`는 실제 자원/소지/행동권·열린 단계, `processed_event_ids`는 실제 적용 event 중복 방지다. 6개 world_delta의 키는 change_coverage의 changed_entity_ids와 일치시킨다. 새 SQL 컬럼/RPC가 아니라 기존 JSON 수납 의미의 일관된 사용이다.
2. 결과가생길때해당현재값과이야기/인물/장면의연결만갱신한다.변화없는전체정보를매번다시쓰지않는다.
3. 저장전원래작업상태에서중요값/관계/출처/입력대기/재개문맥의기준을고정한다.
4. DB1은정확한canon_ref+누적delta/신규/취소/처리event+PC/실행/재개문맥의별도payload를구성한다.현재상태를축소하지않는다.
5. 동결원문·SHA·session/version/event/attempt/parent로 `trpg_v2_commit`→`trpg_v2_verify`→`trpg_v2_load_version`의 같은 version exact read-back. 사용 가능한 인증된 고권한 Supabase 연결에서만 호출하며 공개 API 권한을 열지 않는다.
6. 같은정본과실제read-back으로논리상태를재구성해고정기준과비교한다.등록된값비교와서사문맥충분성/첫장면적용은별도확인한다.
7. 이동표/사용자가 지정한 session/version/SHA가 있으면 exact version을 우선하고 지정이 없을 때만 최신 verified를 읽는다. 파일 인계는 전체 현재 STATE+같은 SHA 정본+생성된 최신 전체 스토리/명세+저장 출처/검증 정보가 필요하며 과거 룰북 파일을 요구하지 않는다. 진행은 현재 소스의 최신 룰북을 쓰고 로컬 검증과 서버 verified를 구별한다.
8. 로드는 첫 지문 전에 지정 상태/정본과 연결된 누적 스토리 전체/명세를 읽고 이야기 흐름·NPC 말투/태도/이유·현재 대화/마지막 질문/준비/확인된 의미·수치/행동 대기를 함께 적용한다. 스토리 전문은 비공개 파일이며 DB 저장 성공만으로 그 파일의 보관/전체 조회 성공을 주장하지 않는다.

신규 rules_version은 배포 RULESET.json의 정확한 식별자를 기록한다. ON 종결의 runtime.hq/ending_state·pcs.player_id/alive 계약은 rules/07-state.md의 STATE_CANON_SAVE_BINDING을 따른다. 기존 저장은 변경하지 않는다.

주기: setup_bootstrap/play_start/40배수안전경계/전체종료·본부ON챕터종료+명시수동. 수동만 정상 저장 뒤 별도 입력으로 스토리 파일을 생성하며 자동 저장은 기존 경험 맥락만 보존한다.기존20턴정본재독은별도이며겹친원문은재사용한다.공개수첩전송은없다.현재상태가남아있는저장실패는플레이를막지않고원문/미저장변경을보존한다.외부차단·상태유실·호환실패를구분한다.현재작업공간/실제서버계약이없는영구메모리는가정하지않는다.

신규 Supabase에서 합성2버전의 실제 commit/verify/exact read-back/SHA·부모충돌·동일attempt·일반접근권한을 검증했다. 실제 비공개 캠페인 정본 파일 원문SHA/절 병합·GitHub 백업왕복·장기 ChatGPT 재현품질은 여전히 미검증이다. 서버 verified가 의미/서사 연속성 완성을 뜻하지 않는다.

## 기존 게임에서 최신 규칙으로 새 저장

1. 프로젝트 지침/룰북 소스를 최신 묶음으로 교체한다. GitHub 갱신만으로 업로드된 파일이 바뀌지는 않는다. 기존 게임의 현재 정본·작업 상태는 그대로 둔다.
2. 같은 게임 채팅에서 다음처럼 요청한다.

   > 현재 진행·수치·소지품·인물 기억·마지막 질문/판정 대기를 유지하고, 소스에 있는 최신 룰북을 적용해 새 세이브를 만들어 줘. 과거 저장은 보존하고 새 버전으로 검증한 뒤 이동표를 줘. 다른 채팅으로 옮길 수 있게 전체 STATE JSON과 비공개 정본 파일도 내보내 줘.

3. 현재 상태가 있으면 과거 세이브 재로드·새 게임 설정/생성을 하지 않는다. 미처리 단계부터 최신 규칙을 적용하고 이미 산출/적용한 값·비용·결과를 중복 처리하지 않는다. 이전 정보가 이미 유실됐으면 실제 원문/기록에서만 복구한다.
4. 같은 session/campaign의 실제 최신 verified parent 다음 새 저장을 만든다. 최신 적용 rules_version과 전환 이력은 새 저장에 기록하고, 과거 checkpoint·정본 원문/해시는 고치지 않는다. 생성 당시 정본의 규칙판과 진행 규칙판은 달라도 된다. 이미 제출한 attempt는 동결 원문으로 복구하고 최신 진행은 다음 저장에 담는다.
5. 저장 성공은 commit→verify→동일 버전 read-back·내용 대조로 확인한다. 파일 내보내기만 한 것/서버 verified·저장 실패와 미저장 범위를 구별한다. 구판 룰북을 갖고 있어야 저장·재개할 수 있는 구조가 아니다.
6. 이 응답 뒤 `스토리 세이브 생성`을 별도 입력한다. 기존 스토리가 없으면 남아 있는 실제 플레이 기록에서만 초기 누적본을 만들고 공백을 명시한다. 구판 전체 이력이 자동 복구되는 것은 아니다.

## 수동 저장과 스토리 파일

사용할 때는 두 번 입력한다.

1. `지금 입력 대기 지점 그대로 저장하고 검증 결과와 이동표를 줘.`
2. 저장 검증 완료 응답을 받은 다음 `스토리 세이브 생성. 이전 전체 기록에 이번 저장까지의 진행을 세세하게 추가하고 파일로 줘.`

두 번째 단계는 최신 누적 `STORY_SAVE_<campaign_id>_r<N>.md`와 `.manifest.json`을 전달한다. 줄거리에는 작은 상황도 남기며 분량 제한을 두지 않는다. 기존 전체 본문을 보존하고 새 구간을 덧붙이므로 최신 전체 파일 하나에 앞 회차도 들어 있다. 정정은 출처를 붙인 추가 기록이며 이전 본문을 몰래 고치지 않는다. 실제 내용/파일 연결 계약은 [STATE_EXPERIENCE_CONTINUITY](../rules/07-state.md#state_experience_continuity)와 [STATE_COMMIT](../rules/07-state.md#state_commit)이 담당한다.

스토리 전문/명세는 **소유자의 비공개 파일/프로젝트 소스**에 보관한다. DB에는 정상 저장 당시 확인한 파일 참조와 요청이 남는다. 생성 직후 파일은 명세가 정확한 저장 SHA와 연결하며 이를 DB 원문에 끼워 넣거나 스토리 때문에 추가 체크포인트를 만들지 않는다. 다음 정상 저장이 생성 완료 참조를 받는다. 따라서 서버 상태만 로드하면 아직 전달/보관되지 않은 스토리 파일까지 생기는 것은 아니다. 파일이 실제 접근 가능한 프로젝트 소스/첨부에 있는지 확인해야 한다.

자동 저장은 추가 입력이나 스토리 파일 생성을 실행하지 않는다. 자동 저장 사이의 실제 경험은 기존 STATE 맥락에 계속 남기고 다음 수동 스토리에 해당 구간도 포함한다. 생성 안내를 나중에 답한 경우 처음 완료한 저장 경계까지만 작성한다. 새 진행까지 포함하려면 더 최신 수동 저장을 요청한다. 파일 생성 실패는 이미 성공한 상태 저장을 취소하지 않는다.

## 다른 채팅으로 옮기는 방법

1. 위의 수동 저장과 추가 입력을 마치고 최신 누적 스토리/명세를 받는다. 열린 장면/판정을 강제로 마치지 않는다.
2. 이동표의 정확한 session/campaign·version/SHA·정본 ID/판본/SHA·rules_version과 스토리 파일/명세명·판본/SHA·수록 끝/공백을 보관한다. 파일 인계는 **전체 현재 STATE JSON + 정확한 비공개 정본 Markdown + 최신 전체 스토리/명세 + 출처/검증 정보**다. 최신 스토리에 포함된 앞 회차 파일을 일일이 다시 첨부할 필요는 없다. 과거 룰북은 필요하지 않으며 실제 비공개 파일은 공개 저장소에 올리지 않는다.
3. 새 채팅에 최신 룰북과 실제 접근 가능한 이동표/전체 파일을 제공한다.

   > STATE_RESUME으로 이 출처·session·지정 version/SHA의 상태·정본과 누적 스토리 전체/명세를 조회해 복원해 줘. 소스의 최신 룰북으로 마지막 질문/판정 대기에서 이어가고 누락은 지어내지 말고 알려 줘.

4. 키퍼는 상태/정본과 지정 지점까지의 **스토리 전체**를 읽는다. 파일명 유사/수정 시각으로 다른 분기/미래 기록을 섞거나 검색 요약만 읽고 전체 조회라고 하지 않는다. 스토리의 과거 값은 당시 이력이며 현재값은 STATE에서 복원한다. PC별 미전달 정보도 자동 공유하지 않는다.
5. 첫 응답의 장소/행동권·질문/메뉴·수치/실물·말투/합의가 이어지는지 확인한다. 로드 자체로 시간 경과·재굴림·소모·보상을 재실행하지 않는다. 스토리가 없던 구판/생성 유보/파일 유실은 실제 확인한 구간과 누락을 밝히며 확인 가능한 상태를 보존한다. 새 채팅 로드가 스토리를 자동 생성하지는 않는다.
6. 서버 저장 실패면 마지막 verified 지점과 이후 미저장 범위를 구별하고 완전한 로컬 파일을 보존한다. 로컬 검증을 서버 verified로 표시하거나 현재 진행을 과거 저장으로 덮지 않는다.

JSON/파일 해시는 바이트 보존을 확인한다. 기록되지 않았거나 유실된 기억, 키퍼의 실제 말투/서술 적용까지 보장하지 않는다. 내부 추론 대신 실제 발언·확인된 결론/행동·출처/인지자를 남긴다.
