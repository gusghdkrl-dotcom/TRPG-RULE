# 룰북·비공개 정본·현재 작업 상태·세이브의 역할

이 문서는 사용 방식과 구현 한계를 설명한다. 실제 캠페인의 비밀·저장 원문을 담지 않으며 게임용 ZIP에는 포함하지 않는다. 실행 규칙은 PROJECT_INSTRUCTIONS와 PRIVATE_CANON_DOCUMENT / PRIVATE_CANON_ACCESS_ROUTER / STATE_CANON_SAVE_BINDING / STATE_WORKING_CONTEXT / STATE_ACCESS_ROUTER / INVESTIGATION_SKILL_ROUTING에 있다.

## 무엇을 어디서 보는가

| 필요한 정보 | 첫 출처 | Supabase 접근 |
|---|---|---|
| 판정 필요 여부, 어떤 기능인지, 성공 단계, 교대 규칙 | 프로젝트의 해당 룰북 절 | 규칙 확인에는 사용하지 않음 |
| PC의 자료조사 수치·행운·현재 위치 | 현재 작업 상태의 PC 시트 | 필요한 값이 실제 유실/충돌한 경우만 복구 |
| NPC 목적·비밀, 증거의 배치·본문 | 현재 작업 상태 → 해당 판본 정본의 NPC/Evidence 절 + 현재 변경 상태 | 변화한 동적 상태가 없을 때 복구 |
| 다른 장소의 예정 사건·위협 진행 | 세이브의 활성 Driver 색인 + 정본의 발동/취소 조건 | 현재 색인/처리 결과가 없을 때 복구 |
| 새 채팅 재개, 저장/검증, 실패 복구, 명시적 저장 대조 | 실제 Supabase 저장 계약 | 해당 작업에 필요한 접근 수행 |

자료 찾기 선언의 정상 흐름은 다음과 같다.

1. 허락·접근 조건·현재 방법을 작업 상태에서 확인한다.
2. 판정 필요 여부는 FICTION_FIRST_ROLL_TRIGGER_GATE, 기능은 INVESTIGATION_SKILL_ROUTING을 적용한다. 문서에서 기록을 찾는 일은 자료조사, 시대적 의미의 전문 해석은 역사다.
3. 판정이 필요하면 현재 PC 시트의 해당 수치와 실제 실패 결과를 사용해 d100을 요청한다. 규칙 본문과 상태가 이미 있으면 규칙 검색도 DB 조회도 0회다. 아직 필요하지 않은 기사 전문이나 흑막 이력을 전부 불러오지 않는다.
4. 굴림 뒤 실제 시간·결과를 반영하고 읽을 수 있게 된 자료 원문을 제시한다. 원문이 이미 있으면 재사용하고, 없으면 필요한 ref를 복구한다. 읽는 행위만으로 저장을 추가하지 않는다.

권한이나 기능 수치가 없는데도 무조건 조회 0회로 밀어붙이지 않는다. 현재 필요한 정보와 없는 이유를 구분해 관련 범위만 복구한다. DB가 부분 조회를 지원하지 않으면 정확한 저장본 한 번에서 필요한 데이터를 가져와 재사용하며, 새 조회 API가 생긴 것처럼 지시하지 않는다.

## 비공개 상태를 AI가 알고 있는가

모델은 실제 생성했거나 도구로 읽어 현재 입력 문맥에 남아 있는 상태를 사용할 수 있다. Supabase에 있는 모든 행이 자동으로 모델의 기억이 되지는 않는다. 룰북에 GM_STATE라고 적는 것만으로 별도의 메모리 서버나 비밀 파일도 생기지 않는다.

현재 배포물은 Markdown 지침/룰북과 배포 검사 스크립트다. 모델 문맥은 독립적인 영구 저장소가 아니며, 대화 압축·새 채팅·문맥 한도로 상세 데이터가 빠질 수 있다. 비공개 추론도 게임 상태를 보존하는 저장 API가 아니다. 따라서 “한 번 로드하면 캠페인 내내 절대 잊지 않는다”는 보장은 하지 않는다.

키퍼가 계속 추적해야 할 범위는 출처/버전과 미저장 변경분, 각 PC의 정확한 수치/위치/진행 대기, 불변 세계의 핵심 제약, 관련 장소/NPC/단서, 다른 장소도 포함한 예정 사건의 발동 조건과 처리 여부다. 매 턴 전체를 다시 쓰지 않고 실제 결과의 변경분을 반영한다. 게임 시간이 경과할 때 예정 사건을 확인하므로 플레이어가 채팅을 보내지 않는 현실 시간에 별도 프로세스가 계속 돌고 있다는 뜻도 아니다.

공개된 지문에 비밀을 숨겨 적거나, 공개 수첩/공개 GitHub에 비밀 요약을 올리는 방식은 사용하지 않는다. 소유자가 요청한 키퍼용 정본 문서만 PRIVATE_CANON_DOCUMENT 절차로 프로젝트 소스에 제공한다. 현재 키퍼용 데이터가 있다고 해서 플레이어 화면으로 공개해도 된다는 뜻은 아니다. 이 규칙의 공개 범위는 게임 진행 규약이며, 클라이언트의 도구 결과 표시나 계정 접근권을 기술적으로 차단하는 보안 구현은 아니다.

## 현재 채택한 운영: 시작·30턴 저장에서 전체 복기

2026-10-30 사용자 결정으로 전용 게임 서버/상주 메모리 방안은 폐기했다. 현재 프로젝트의 지침 라우팅과 기존 Supabase 저장을 유지한다. 일반 턴에는 확인한 규칙과 현재 작업 상태를 재사용하고, 실제로 필요한 데이터가 없을 때만 한정 복구한다. 룰북은 규칙의 출처이며 특정 캠페인의 비밀이나 실제 PC 수치를 대신 제공하지 않는다.

게임 시작과 Scene Turn 30/60/90… 저장의 안전 경계에는 STATE_CHECKPOINT_RECAP을 수행한다. 저장 전 현재 전체 상태와 변경 근거를 검사하고, 저장 후 같은 version의 verified 진행 상태와 해당 저장 모드의 정본을 결합해 NPC/단서·화면 밖 예정 사건·PC/난수/진행 대기를 복기한다. DOCUMENT_BOUND는 불변 전문을 매번 다시 읽지 않고 색인·coverage와 현재 변화, 필요한 절을 확인한다. 다음 장면과 발동 조건을 정리하되 미래 진행을 미리 만들어내지 않는다.

복기는 저장 검증에 이미 필요한 원문을 재사용한다. 같은 데이터를 다시 읽거나 별도 저장본을 만들지 않으며 복기 내용은 플레이어 지문·HUD·수첩에 출력하지 않는다. 일부 본문이 잘린 응답이나 성공 상태 코드만으로 전체 복기를 마쳤다고 처리하지 않는다. 이것은 문맥을 다시 확인하는 운영 절차이며 다음 30턴의 기억을 보장하는 기능은 아니다.

새 채팅에서는 검증된 저장본부터 같은 복기로 재개한다. 마지막 저장 이후 변경분을 잃었다면 과거 저장과 현재 상태를 임의로 섞지 않고 복구 가능한 지점을 분명히 한다. 정상 턴의 반복 조회를 줄이더라도 필요한 저장 검증과 실제 유실 복구는 유지한다.

## 검증 범위

사용자가 보고한 합본 열람 응답은 약 64초였다. 제공된 텍스트에는 규칙 검토가 보이지만 실제 RPC명·횟수·시간은 없어 Supabase 호출 여부나 병목은 확정할 수 없다. 현재 변경은 조회 기준과 상태 유지 계약을 명확히 한 것이며, 실제 게임 모델의 기억·응답 시간 또는 운영 DB를 실행 검증한 결과가 아니다. 측정은 RESPONSE_TIME.md를 따른다.

## 정본과 진행 세이브의 결합

신규 세계 정본은 세계 생성 후 한 번 확정해 소유자가 파일로 받고 프로젝트 소스에 업로드한다. 파일 식별/판본·절/entity ID를 실제 조회한 뒤 사용한다. 일반 턴의 NPC 반응·단서·법칙·장소·시간 경과·엔딩 판정은 PRIVATE_CANON_ACCESS_ROUTER의 해당 절로 이동한다. 읽은 사실은 현재 변경 상태를 적용한 뒤 공개 범위를 걸러 사용한다.

예를 들어 NPC_BASELINES에 생존 상태로 쓰인 NPC가 현재 저장에서 사망했다면 사망 상태가 유지된다. 단서가 옮겨졌으면 현재 위치를 쓰고, Driver가 취소됐으면 정본의 예정 시각이 되어도 발동하지 않는다. 현재 변경 기록 자체가 유실됐다면 최초 상태를 현재값으로 가정하지 않는다. 새 NPC와 최초 확정한 자료 원문은 다음 정본 개정 전까지 세이브의 추가 사실로 보존한다.

저장량을 줄이는 DOCUMENT_BOUND는 정확한 정본 참조 + 완전한 현재 상태 + 정본 이후 누적 변화/추가 사실을 저장한다. 최신 세이브 하나와 정확한 정본으로 재개할 수 있어야 하며 delta 체인을 매번 재생하지 않는다. 서버가 이를 지원하는지 확인 전에는 LEGACY_FULL 전체 저장을 유지한다. 기존 저장은 소급 삭제/변환하지 않는다.

이번 패치는 룰북 계약과 라우팅이다. 저장 서버/어댑터 도구가 이 작업 환경에 없어 DOCUMENT_BOUND의 commit·verify·새 채팅 복원은 실행 검증하지 못했다. 실제 프로젝트 소스 검색·파일 생성 기능도 게임 실행 환경에서 확인해야 한다. 운영 도입 전에는 정본 참조 보존, 누적 변화·삭제/사망·추가 사실 round-trip, 판본 누락 시 중단, 열린 판정/RNG 재개를 서버의 실제 계약으로 점검해야 한다.

세이브 실패는 시작·첫 장면·일반 진행·인계·엔딩을 막지 않는다(STATE_SAVE_FAILURE_CONTINUE). 현재 작업 상태로 계속하며 저장 성공은 실제 검증 때만 표시한다. 실패한 원문은 동결하고 이후 진행과 구분해 다음 저장 경계/수동 저장/연결 복구 때 최신 상태를 저장한다. 미저장 진행이 새 채팅에서도 복원된다고 보장하지 않으며, 실제 데이터 유실은 필요한 범위를 복구한다.

## 정본 재독 20턴 / 세이브 30턴

PRIVATE_CANON_PERIODIC_REVIEW는 Scene Turn 20/40/60…의 첫 안전 경계에서 활성 판본 전체를 실제 소스 조회한다. 기억/요약 재사용만으로 정기 읽기를 대체하지 않는다. 숨은 진실·모든 NPC/단서/Driver·종결 조건까지 manifest의 전체 절을 확인하고 최신 세이브+미저장 변화를 적용한다. 검색 발췌·본문 잘림은 미완료다.

30턴 저장과는 독립이고 60/120…에서는 읽기 1회를 공유한다. 저장 실패해도 재독은 수행하며, 재독 실패 자체도 이미 확인된 사실로 가능한 플레이를 막지 않는다. 현재 사실이 실제 없으면 해당 결과의 한정 복구를 수행한다. 소스 읽기를 위해 매번 Supabase full load를 추가하지 않는다.

초기 업로드·판본 전환·새 채팅에도 전체 재독을 한다. 대화에는 비밀을 출력하지 않고 재독 완료 시점·판본·확인 범위와 다음 경계를 실제 작업 상태에 남긴다. 문맥의 영구 유지나 도구의 전체 파일 반환을 보장하는 구현은 아니다.
