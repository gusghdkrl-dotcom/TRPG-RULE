# 규칙 편집 절차

사용자의 문제·아이디어·피드백은 현재 규칙과 영향을 먼저 확인한다. 적용·수정 지시가 있으면 해당 범위의 편집·검증·개발 일지·GitHub 반영까지 수행한다. 이번 세션에서는 전체 1차 정리와 명시한 기능 제거가 승인됐다.

1. 현재 Git 상태와 원격 기준을 확인해 기존 변경을 보존한다.
2. RULE_CATALOG와 현재 규칙 ID로 담당 절과 연결된 상태·출력을 찾는다.
3. 게임 동작 변경과 문장/구조 정리를 구분한다. 모호한 게임 설계는 사용자에게 알려 판단받는다.
4. 해당 규칙 본문을 갱신한다. 뒤에 버전별 Override를 쌓거나 다른 파일에 상세 수치를 복사하지 않는다.
5. 새/삭제 ID의 참조를 갱신한다. Project Instructions는 7,800자 이내로 유지한다.
6. `python3 scripts/rulebook.py check`와 관련 대표 사례를 대조한다. 이 도구는 문서 검사이며 AI 플레이나 서버 API를 실행하지 않는다.
7. 매 패치에서 `python3 scripts/rulebook.py export`를 실행한다. 배포용 `dist/TRPG-RULE-project.zip`의 변경을 룰북과 같은 커밋에 포함한다. 같은 입력이면 ZIP도 동일하므로 문서 외 변경만 있을 때 ZIP diff가 없는 것은 정상이다. `build/`는 로컬 작업물로 유지한다.
8. DEVLOG에 변경 이유·내용·실행한 검증·미검증 영역을 기록하고 커밋·푸시한다. GitHub main의 룰북과 배포 ZIP을 함께 반영하며, README의 고정 다운로드 주소를 유지한다. 강제 푸시하지 않는다.

비공개 실제 게임 상태·키·토큰을 저장소에 커밋하지 않는다. 문서 변경 권한은 운영 DB 삭제·권한 변경·다른 저장소의 앱 배포를 자동 포함하지 않는다. 운영 변경이 필요하면 실제 계약을 읽고 그 작업 범위를 구체적으로 확인한다.
