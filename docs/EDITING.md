# 규칙 편집 절차

**매 패치 시작 시 [PATCH_POLICY.md](PATCH_POLICY.md)를 먼저 읽는다.** 공통 준수 기준은 그 문서가 소유하고, 이 문서는 파일별 배치와 실제 편집·검증·배포의 세부 절차를 다룬다. 완료 전에 패치 규정의 관련 항목으로 결과를 대조한다. 사용자 요청과 이미 확정한 결정·승인 범위를 우선한다.

이 절차의 목표는 **룰북의 문장 수를 늘리는 것**이 아니라 실제 플레이 실패를 고치고, 기존 기능을 보존하면서 AI 키퍼가 동일한 상황에서 올바르게 행동하도록 만드는 것이다. 분석·계획 요청은 반영 승인과 구분한다. 적용 지시가 있다면 가능한 범위에서 수정·검증·기록·GitHub 반영까지 수행한다.

## 인스트럭션과 룰북의 역할

이 원칙은 앞으로 모든 신규 규칙·패치·인스트럭션 재편에 적용한다. `PROJECT_INSTRUCTIONS.md`는 **진행 중 항상 적용 여부를 살필 필수 행동 계약**으로 압축하고, 수치·절차·예외의 실제 권위는 해당 판본의 담당 원문에 둔다. ‘항상’은 매 턴 모든 절차를 실행하거나 전체 룰북/정본을 재독·전수 검수한다는 뜻이 아니다.

| 배치 | 포함할 내용 | 편집 기준 |
|---|---|---|
| 프로젝트 인스트럭션 | 상시 행동 원칙·중요 발동 게이트·담당 원문으로 가는 짧은 참조 | 현재 입력/상태에서 무엇을 판단·보존하고 언제 원문을 적용할지 명료하게 적는다. |
| 담당 룰북 | 판정/피해·HP/SAN·치료/광기·카드 등 세부 조건·수치·계산·예외·개별 효과/자료, 저장/복원·UI/연결 계약 | 기능을 소유한 절 한 곳에서 정의하고 실제 발동 시 원문 전체를 따른다. |
| START_GAME/04-setup | 설정·원작 확인·PC/세계 생성·초안 대조·공동 출발·메인 봉쇄/최종 보스 준비·본부 입단/출격 | 그 단계의 실행 절차를 둔다. 진행 인스트럭션에는 확정된 정본/상태와 발동 경계를 지킬 의무만 남긴다. |
| templates/PRIVATE_CANON_TEMPLATE.md | 04의 준비 결과를 07의 정본 필수 절에 실제 사실/ref로 작성하는 공개 빈 폼 | 생성/정본 관련 패치의 영향 범위로 함께 대조한다. 담당 룰북을 참조하고 규칙/수치 전문·별도 권위를 중복하지 않는다. 실제 캠페인 정본/세이브와 구별한다. |

상시 요약은 **규칙 적용/조회, 정본/누적 상태, 입력/열린 단계, PC 주도권/대사, 인물별 정보/공개, 판정 발동, 실제 난수, 시간/행동권, 능동 세계/후속, 위해/공포·생사/인계, NPC 자율성/기억, 단서/추리, 장면/호흡, 다인 협동, 실물/자원·모드, 사건/목적·종결, 행동 안내/HUD·시각화, 상태 갱신/재독·저장/복원**의 누락을 해당 변경 범위에서 확인한다. 이는 고정18절/헤더나 문장 수·형식을 강제하는 목록이 아니다.

- 조건부 규칙·준비/자료로 배치해도 필수성이 약해지지 않는다. 예를 들어 HP0 구조·SAN0·중상/치료, 재장전/대항·상쇄·카드별 효과는 발동 시 정확한 원문 조건/예외까지 집행한다. 압축본이나 일반 CoC 기억으로 대신하지 않는다.
- 새 결함은 원인 담당 본문과 직접 호출부에서 고친다. 오류 사례·개별 시나리오/NPC/보스·표/계산·RPC 인자를 매번 상위 인스트럭션에 추가하지 않는다. 상시 발동 인지가 필요한 변경만 짧은 게이트/라우팅을 함께 고친다.
- 압축 전후에 **적용 시점/대상·선행 조건·PC 입력/동의·효과/상태 변화·예외·공개 범위·실패/재개·비소급과 담당 절 호출**이 보존됐는지 해당 원문과 대조한다. 조건을 생략해 뜻을 넓히지 않는다. ‘시트/지도 열람0시간’을 모든 극중 독서0시간으로, ‘임의 지급 금지’를 실제 발견/선물 금지로 축약하는 식의 의미 변경을 금지한다.
- 같은 조건을 여러 파일에 전문 복사하거나 새 Override로 덮지 않는다. 통합/이관하면 중복·상반·충돌·끊긴 참조/폐기 호출과 관련된 낡은 검증 문구도 함께 정리한다. 유효한 조건·기능·구판 호환을 삭제해 검사를 맞추지 않는다. 신규/기존 게임의 진행 권위는 현재 프로젝트 소스의 최신 룰북이다. 과거 저장 원문/확정 결과는 보존하고 새 저장에 실제 적용 규칙을 기록하며, 구판 룰북 파일을 재개 필수물로 요구하지 않는다(STATE_IDENTITY).
- 프로젝트용 인스트럭션은 각각 공백·줄바꿈 포함 **7,800자 이하**로 실제 계산한다. 상한은 채울 분량이 아니다. 가능한 간결하게 여유를 남기되 정확성·발동 조건·서술/HUD·저장 검증을 깎지 않는다. 짧아졌다는 사실만으로 준수율/품질·응답 속도 향상을 입증했다고 하지 않는다.

작은 패치마다 전180개 규칙 재분류·새 검토 장부/검증 체계를 만들 필요는 없다. 인스트럭션 전체를 재편할 때는 관련 규칙의 배치/호출 누락을 전체 범위로 대조하고, 국소 패치는 직접 영향받는 범위를 대조한다. 아래의 최소 검증·배포 절차를 그대로 적용한다. 보관된 과거 초안/개발 문서보다 이 편집 원칙과 현재 담당 게임 원문을 우선한다.

## 1. 현재 정본 및 문제 확인

1. GitHub `main`의 최신 HEAD·관련 커밋·기존 변경을 확인해 다른 작업을 덮어쓰지 않는다. 개발 브랜치·옛 설계서·DEVLOG를 `main`보다 우선하지 않는다.
2. 사용자 피드백의 **관측된 장면/출력**과 추정 원인을 분리한다. 신규/재개, 본부 ON/OFF, 인원·각자의 상태, 직전 사용자 입력, 저장·공개 범위 등 확인된 재현 조건을 기록한다. 불명확한 조건은 단정하지 않는다.
3. 플레이어가 실제로 겪어야 할 경험, 피해야 할 결과, 변경 후 관측 가능한 키퍼 행동을 정한다. 핵심 선택·대사·감정·추론·수락을 키퍼가 대신하지 않도록 한다.

## 2. 담당 절과 영향 범위 조사

4. `PROJECT_INSTRUCTIONS.md` → `START_GAME.md`/현재 상태 → `rules/00-index.md`와 `docs/RULE_CATALOG.md` → 담당 `rules/*.md`의 실제 본문·참조 순서로 추적한다. 원인을 **규칙 누락 / 호출·라우팅 누락 / 상충·중복 / 입력·상태 전이 누락 / 기술 미구현**으로 구분하고, 수정 내용을 위 역할에 맞는 담당 위치에 배치한다.
5. **신규 규칙을 추가하는 경우에도 반드시 영향 범위를 확인한다.** 같은 행동을 규정하는 기존 절, 발동 조건·우선순위, 입력 대기/재개, 상시 지침/시작점/색인, 작성 템플릿, 테스트 계약과 배포 대상의 의존 관계를 확인한다. 생성/원작 변주·정본의 필수 내용/절·적/자원 수치의 준비·E/최종 경로 검토·저장 연결이 바뀌면 `templates/PRIVATE_CANON_TEMPLATE.md`의 관련 작성 항목과 담당 ref를 대조·갱신한다. 새 규칙과 충돌하는 문구는 원문에서 수정하고, 폼에 남은 폐기 항목/옛 수치·참조와 불필요한 중복·구버전 Override를 제거한다. 영향이 없으면 폼을 억지로 수정하지 않는다. 양식 갱신으로 실제 캠페인의 이미 작성된 정본/세이브를 자동 재작성하지 않는다.
6. **기능을 잃은 잔존 지시**도 정리한다. 삭제·통합한 기능을 여전히 호출하는 메뉴, 선택지, 규칙 ID, 예전 수치, 도달 불가능한 분기, 더 이상 유효하지 않은 참조·검증 앵커를 찾아 수정/삭제/이관한다. 단순히 당장 등장하지 않았다는 이유만으로 유효한 기능이나 기존 정본·세이브 호환 경로를 제거하지 않는다. 역사 자료는 실행 지시로 다시 연결하지 않는다.

## 3. 최소 구현과 플레이 계약

7. 담당 절 한 곳에 **적용 시점·선행 조건 → 키퍼의 행동/출력 → 플레이어 입력 대기 → 상태 변경 → 금지할 지름길 → 예외·재개·비소급** 중 필요한 내용을 실행 가능한 문장으로 적는다. 새 지시를 파일 끝에 덧붙여 이전 지시를 덮지 않는다.
8. 실제 원인을 가진 본문과 **직접 연결된 호출부·라우터·색인·검증 계약**만 함께 수정한다. 변경한 규칙을 사용할 때 기존 규칙이 어떻게 달라지는지, 어떤 기능과 상태를 그대로 보존하는지 대조한다. 무관한 HP/SAN·카드·보상·시간·서사·저장/DB 설계를 함께 바꾸지 않는다.
9. 변경한 행동에 대해 **성공 사례 하나와 발생하면 안 되는 실패 반례**를 우선 준비한다. 플레이어의 거부/유보, 조기 해결, 확보한 안전, NPC의 실제 정보·위치, 기존 세이브 등 영향받는 경계만 검토한다. 모든 게임 모드를 매번 기계적으로 전수 조사하지 않는다.

## 4. 필요한 만큼만 검증

10. 룰북·시작점·프로젝트 지침·작성 템플릿이나 배포용 자산/빌드가 바뀌면 `python3 scripts/rulebook.py check`로 **규칙 ID·참조·색인·금지 구문·지침 길이·폼의 존재/필수 절 등 구조 무결성만** 확인한다. 템플릿의 필수 절은 PRIVATE_CANON_DOCUMENT의 실제 목록과 일치시킨다. 구조 검사가 작성 항목의 의미/수치·충돌 대조를 대신하지 않는다. 기존 180개 문구 앵커 검사는 `python3 scripts/rulebook.py deep-check`로 따로 남기되 일상 패치의 의무 검사로 사용하지 않는다. 과거 문구에 묶인 심층 검사가 실패해도 이를 무조건 현재 규칙 결함으로 해석하지 않는다. 바뀐 기능과 직접 연관된 **기존** 회귀 테스트만 추가로 선택 실행한다. 실재하는 새 결함을 기존 검사로 보호할 수 없을 때에만 작은 부정 회귀를 추가한다. 일괄 전체 테스트·새 검증 프레임워크·무관한 보안/DB 검사는 기본값이 아니다.
11. 검사가 실패하면 먼저 **실제 오류와 해당 변경의 관계**를 확인한다. 정당한 기존 불변조건이 깨졌으면 규칙을 고치고, 폐기된 문구에 매인 낡은 검증이라면 해당 앵커를 의미에 맞게 최소 갱신한다. 검사에 맞추려고 무관한 규칙을 바꾸거나 검사를 근거 없이 확장하지 않는다. `rulebook.py check` 통과는 AI의 실제 장면 실행이나 API 성공을 입증하지 않는다.
12. 저장·보상·본부 API를 실제 수정했을 때만 해당 검증 환경에서 관련 계약을 시험한다. 운영 DB 쓰기·삭제, 권한 변경, 다른 저장소 앱 배포는 별도 승인과 검증이 필요하다. 실제 플레이를 실행하지 않았으면 **실전 미검증**으로 기록한다.

## 5. 배포, CI, 완료 보고

13. 게임용 `PROJECT_INSTRUCTIONS.md`, `START_GAME.md`, `rules/*.md`, `templates/*.md`, 승인 자산이나 ZIP 생성 로직이 바뀌면 `python3 scripts/rulebook.py export`를 실행해 `dist/TRPG-RULE-project.zip`을 갱신한다. 원칙적으로 소스/폼과 ZIP을 같은 커밋에 넣는다. 템플릿은 ZIP·UPLOAD_GUIDE·README 설치/교체 안내와 SHA256 manifest에 포함하고 `templates/**` 변경도 자동 ZIP 갱신 경로에 유지한다. 실행 소스12개의 RULESET 식별과 폼의 파일 hash를 구별한다. 동일 입력에 ZIP 차이가 없다면 정상이다. 개발 문서/DEVLOG만 바뀌어 배포 입력이 그대로인 경우에는 재생성을 강제하지 않는다. `build/`는 로컬 작업물이다.
14. `DEVLOG.md`에 **재현/근본 원인, 변경 파일·규칙 ID, 제거한 충돌·잔존 기능, 보호한 동작, 실행한 검사와 미검증 영역**을 간결히 적고 GitHub에 반영한다. `main`의 최종 변경과 필요 시 ZIP 일치 여부를 확인하며 README 고정 다운로드 URL을 유지한다. 강제 푸시하지 않는다.
15. CI는 **필수 종료 대기나 전체 테스트 승인 관문이 아니다.** 자동 ZIP 작업은 기본 문서 검사·내보내기로 가볍게 두고, 세부 회귀는 실제 변경 영향에 맞춰 선택한다. Run ID·상태·마지막 결과를 한 번 확인하고, 진행 중이라면 필요한 경우에만 동일 실행을 최대 3회 확인한다. 장시간 진행되면 상태를 기록하고 다른 개발을 계속한다. 실패는 실제 로그로 원인을 고치며 무관한 테스트를 늘리지 않는다.

## 상시 보호

어떤 패치도 플레이어 주도권·공개 범위·실제 확보한 안전, 1~3인의 개별 행동권, 기존 검증 정본·세이브, 본부 ON/OFF의 분기와 이미 확정된 보상/성장을 근거 없이 되돌리지 않는다. 인스트럭션의 배치·압축/길이는 위 [인스트럭션과 룰북의 역할](#인스트럭션과-룰북의-역할)을 따른다. 비공개 정본·인증정보·실제 세이브를 GitHub나 ZIP에 넣지 않는다.
