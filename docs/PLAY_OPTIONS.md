# 게임 운영 방식 결정

결정일: 2026-10-30. 사용자는 전용 게임 서버·상주 메모리 시스템 방안을 폐기하고 현재 프로젝트 방식을 유지하기로 했다. 새 서버·전용 채팅 화면·추가 상태 API를 이번 작업의 후속 계획으로 두지 않는다.

## 채택: 프로젝트 지침·분야별 룰북·기존 Supabase

일반 턴은 프로젝트 지침의 상황별 경로로 필요한 규칙 ID만 참조한다. 현재 문맥에 남아 있는 같은 판 본문은 재사용한다. 실제 PC 수치·NPC 지식·단서·예정 사건은 현재 생성/로드된 작업 상태를 사용하며, 룰북의 예시로 캠페인 상태를 대신 만들지 않는다.

Supabase는 시작/새 채팅 복원, 실제 누락·충돌 복구, 기존 저장 주기와 검증, 명시적 DB 대조에서만 접근한다. 이동·자료조사 판정·NPC 대화·HUD·PC 인계라는 이유로 조회하지 않는다.

게임 시작과 Scene Turn 30/60/90… 저장 경계에 STATE_CHECKPOINT_RECAP을 수행한다. 저장 전 전체 상태와 변경 근거를 점검하고, 저장 후 같은 verified 진행 원문과 저장 모드별 정본으로 현재 장소 밖 NPC/단서/예정 사건·전원 PC/난수/진행 대기를 복기한다. 다음 장면의 작업 문맥을 정리하되 원문을 버리거나 비밀을 공개하지 않는다. 복기 때문에 동일 데이터 조회·별도 저장·사건 재실행을 추가하지 않는다.

## 장면 운영

공개 장면과 단서는 P1~P3의 공통 지식이며 실제 위치·자원·행동권은 구분한다. NPC가 새 답변이나 수락을 요구하면 플레이어에게 선택을 돌린다. 플레이어가 직접 말했거나 질문/설명/일감 문의를 선언한 부분은 직접화법으로 보여준다. 단순 이동에 새 PC 대사를 만들거나 목적 단위 압축으로 협상·계약까지 대신 끝내지 않는다.

## 실제 한계와 측정

문서만으로 무손실 기억·정확한 실행·응답 시간을 보장할 수는 없다. 전체 복기는 기존 저장 시점에 정확한 데이터를 다시 확인하는 절차이며 영구 비밀 메모리를 추가하는 기능이 아니다. 저장 사이에 실제 정보가 유실되면 한정 복구하고, 미저장 변경분을 재구성할 근거가 없으면 그 영향을 받는 결과만 보류한다.

일반 턴과 시작/30턴 저장의 응답 시간을 구분해 측정한다. 실제 도구 로그에서 동일 규칙·동일 version의 반복 조회를 먼저 확인한다. 상세 데이터 흐름은 [STATE_FLOW.md](STATE_FLOW.md), 측정 방법은 [RESPONSE_TIME.md](RESPONSE_TIME.md)를 따른다.

## 생성 입력 UI의 지원 조건

게임 실행 대상은 일반 ChatGPT 프로젝트 채팅이다. 이 저장소는 Markdown 룰북과 ZIP 생성 도구이며 채팅 클라이언트의 입력 컴포넌트를 구현하지 않는다. 코드 블록·Markdown 표·HTML 코드 출력은 제출 가능한 폼이 아니다.

현재 게임 채팅에 실제 입력 UI 도구가 제공되면 SETUP_UI_FIXED_CONTRACT에 따라 사용한다. 지원 여부는 해당 채팅의 호출 가능한 도구와 실제 렌더링·제출로 확인해야 한다. Codex의 질문 도구가 작동했다는 사실은 일반 ChatGPT 프로젝트의 지원 증거가 아니다. UI 도구가 없으면 문서 수정만으로 폼을 활성화할 수 없으며, 사용자 선택으로 채팅 입력을 사용한다. 별도 웹앱/서버 도입은 이 수정에 포함하지 않는다.

비공개 정본은 소유자에게 파일로 제공해 프로젝트 소스로 조회한다. 현재 진행은 세이브·로드로 유지하며 정본 기준선에 현재 변화를 적용한다. 저장량 축소는 STATE_CANON_SAVE_BINDING의 서버 호환 확인이 필요하고, 미확인 시 기존 전체 저장을 유지한다.
