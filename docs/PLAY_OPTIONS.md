# 게임 운영 방식 검토

검토일: 2026-10-29. 이번 작업은 문서 개편이며 아래 대안을 구현·배포하지 않았다.

## 현재 권장: 프로젝트 문서 + 실제 Supabase 저장

현재 사용 방식에서 비용과 유지보수 부담이 가장 작은 선택이다. 최신 실행 문서만 올리고, 색인의 규칙 ID로 필요한 절을 조회하며, 공개 대화와 비공개 상태를 구분한다. 불변 세계 핵심과 변화하는 상태는 각각 정본으로 보존한다.

장점은 채팅으로 바로 플레이하고 원작/연출을 유연하게 바꿀 수 있다는 점이다. 한계는 필요한 파일의 검색, 긴 대화에서의 상태 유지, 정확한 난수·수치·저장 호출을 모두 모델의 실행에 의존한다는 점이다. 문서가 짧아져도 그 문제가 자동으로 사라지지는 않는다. 주기 저장 사이의 미저장 진행도 복원이 보장되지 않는다.

**공개 장면과 단서는 파티 공통 지식이다.** 2~3인 모두 같은 정보를 사용하고 물리적 위치·자원·행동권만 구분한다. 숨겨야 할 대상은 아직 발견되지 않은 세계·NPC·증거 상태이며 실제 게임의 비공개 상태를 공용 프로젝트 파일에 올리지 않는다. 첫 복원 이후는 작업 상태를 유지하고 실제 저장/복구 조건에서만 Supabase를 접근한다.

## 다음 단계: 규칙 조회·상태 검증 도구를 추가한 채팅

읽기 전용 `규칙 ID → 정확한 본문/현재 판` 조회와, 상태 읽기·검증·Checkpoint 도구를 갖추는 방식이다. 현재 안정된 ID를 활용할 수 있다. 난수 생성·특성 샘플링·성공 단계·피해·hash·동시 쓰기 검증을 도구에 맡기고 AI는 선언 해석·NPC·장면을 담당하게 할 수 있다.

이 방식은 조회 누락과 계산/직렬화 오류를 줄일 수 있지만 도구의 계약·권한·테스트가 필요하다. 현재 repository에 실제 게임 서버는 없으며 해당 도구가 이미 연결된 것처럼 운영해서는 안 된다. 사용자에게 모델의 내부 사고 기록을 보존시키는 방식이 아니라, 확정된 게임 상태와 검증 가능한 사건 결과를 저장한다.

## 더 큰 대안: 전용 게임 서버와 플레이어 화면

서버가 세계/PC의 상태와 난수·판정·버전·이벤트/Checkpoint·사용자별 읽기 권한을 관리하고, AI 키퍼는 그 상태를 바탕으로 이야기와 선택 결과를 설명한다. 파티 공개 정보와 비공개 세계를 분리하면서 채팅방 이동·재시도·동시성을 관리할 수 있다. PC별 비밀 화면은 현행 게임 방향에 필요하지 않다.

초기 구현·운영 비용이 가장 크다. 이번 1차 정리 뒤 게임 방향을 확정하고, 반복되는 실제 오류를 확인한 후 도입 범위를 정하는 편이 적절하다. 기존 Supabase를 유지하면서 필요한 부분부터 추가할 수 있으며 전체 앱 재개발이 첫 단계일 필요는 없다.

## 권고

지금은 정리한 프로젝트 문서 + 연결된 Supabase의 실제 검증 저장을 사용한다. 현재는 지침의 직접 라우팅·조건부 DB 접근·장면 묶음 교대를 우선 적용한다. 그래도 지연이 남으면 실제 호출 기록으로 규칙 검색·상태 직렬화·모델 지연을 나눈 뒤 저장 호출의 서버 검증과 필요한 조회 API부터 확정한다. 이후 실제 문제 빈도에 따라 규칙 조회·판정 도구를 추가한다. 프롬프트만으로 완전한 메모리·정확한 난수·비공개 채널을 보장한다고 약속하지 않는다.
