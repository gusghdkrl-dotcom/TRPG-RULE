# 응답 시간 개선과 측정

2026-10-29 사용자 테스트에서 일반 응답이 약 1분 걸렸다는 보고를 받았다. 이 저장소 작업에서 해당 세션의 도구 호출 시간이나 모델 처리 시간을 직접 측정하지는 못했다. 따라서 원인을 문서 검색 하나로 단정하거나 개선 후 20초를 보장하지 않는다.

추가 테스트에서는 짧은 이동 1분 28초, 자료 확인 1분 14초, 인계 입력 뒤 도착 처리 40초가 보고됐다. 로그에는 규칙 대조와 반복 인계가 보이지만 실제 RPC 목록·호출 시간이 없어 매 지문 Supabase 조회를 했다고 확정하지 않는다. 실제 캠페인의 이름·단서·저장 원문은 이 문서에 복사하지 않는다.

## 이번에 적용한 것

- 프로젝트 지침에서 입력 상황 → 파일/규칙 ID로 직접 라우팅한다. 같은 대화에서 확인 가능한 동일 규칙판 본문을 재사용하며, 원문 유실·변경·실제 불확실성이 있는 절만 조회한다.
- Supabase는 STATE_ACCESS_ROUTER의 로드·상태 유실/충돌·저장 검증·실패 복구·명시적 대조 조건에만 접근한다. 첫 연결/실제 변경 때 확인한 대상·함수 계약은 재사용한다. 일반 이동·대화·HUD·A는 기본 DB 조회 0회다.
- 공개 정보는 파티 공통으로 처리해 PC별 FOG 재대조와 전달 대기를 제거했다. 자원·소유·물리적 현장·직접 노출은 PC별로 유지한다.
- 짧고 독립적인 이동은 출발~도착을 한 응답에 처리한다. Spotlight 누적 15분 초과나 실제 동시간 충돌 때만 병렬 선언을 수집한다. 비전투 3회 목표·5회 상한으로 이동 단계마다 인계를 반복하지 않는다.
- 매 턴 불변 세계·전체 NPC·전체 저장본을 재요약하지 않는다. 이번 행동과 실제 시간에 영향을 받는 상태만 갱신한다. 저장 시에는 기존의 전체 snapshot 및 verify/read-back을 유지한다.
- 직업·낯선 풍경·상황의 첫 설명에는 웹 참고를 한 차례 묶어 탐색할 수 있다. 같은 자료를 재사용하고 적합한 결과가 없으면 텍스트를 계속 제공한다. 참고 이미지 활용이 실제 응답 시간을 줄였는지는 별도 측정한다.
- 일반 텍스트 장면은 대략 300~600자를 기준으로 핵심 변화·대사·선택을 보여준다. 중요한 장면은 필요한 만큼 확장한다. 소지품과 HUD 중복을 줄이고 불필요한 웹 검색·이미지 호출을 하지 않는다.
- HUD의 아이콘·표·목록은 같은 공개 상태의 텍스트 서식이다. 장식용 생성 이미지·웹 검색·DB 조회를 추가하지 않으며 반복되는 전체 소지품·설명문은 늘리지 않는다. 서식 변경의 실제 지연 영향은 별도로 측정한다.
- 수리·업무·서류 조회를 목적 단위로 처리해 하나의 결과를 얻기 위한 왕복 응답 수도 줄인다. 이는 한 응답의 지연과 별개로 플레이 속도를 개선한다.

20초는 일반 텍스트 턴의 목표다. 생성, 이미지, Supabase 저장·복원, 플레이어 굴림 입력 대기는 별도로 본다. 빠른 응답을 위해 필수 판정·정보 공개·저장 검증을 생략하지 않는다.

## 요청 유형별 기대 도구 사용

| 조건 | 규칙 검색 | Supabase | 출력 |
|---|---|---|---|
| 본문·상태가 남아 있는 확인된 짧은 이동 | 0회 | 0회 | 실제 중단 없으면 도착과 다음 선택 |
| 같은 자료 재표시·공개 지도·일반 대화·인계 A | 캐시된 본문 재사용 | 0회 | 필요한 사실/장면만 |
| 새 규칙이 필요한 판정·위협 | 누락된 해당 ID만 | 상태 유실/저장 경계가 아니면 0회 | 실제 판정·결과 |
| 새 채팅 로드 | 복원 규칙·현재 열린 절차 | 필수 verified 복원 | 기존 상태에서 재개 |
| 저장 경계·유실/충돌·실제 복구 | 해당 저장 규칙 | 필수 parent/verify/read-back/복구 | 실제 검증 결과 |

이는 문서상 실행 목표이며 측정된 호출 수가 아니다. 일반 턴이 저장 경계와 겹치면 필수 저장 호출을 수행한다.

## 실제 측정 방법

같은 모델/설정과 같은 규칙판에서 일반 행동 응답을 최소 20개 기록한다. 사용자 입력 제출부터 첫 글자와 응답 완료까지의 시간을 나누고, PC 굴림값을 기다리는 사람의 시간은 제외한다. 도구별 시간은 실제 제공될 때만 기록하며 추정해서 채우지 않는다. 규칙 검색/RPC의 이름·횟수·재조회 사유와 일반 입력/A 확인/굴림 입력을 구분한다. 2~3인에서는 마지막 실제 선택부터 다시 선택할 때까지의 실제 대기 시간도 함께 측정한다.

| 응답 종류 | 첫 글자까지 | 완료까지 | 실제 도구 호출·시간 | 정확성 확인 |
|---|---|---|---|---|
| 일상 대화·관찰 | 측정 대기 | 측정 대기 | 측정 대기 | 사실·선택·공개 범위 |
| 목적 단위 수리·조사 | 측정 대기 | 측정 대기 | 측정 대기 | 선언 범위·판정·시간·보수 |
| 굴림 결과 처리 | 측정 대기 | 측정 대기 | 측정 대기 | 성공 단계·자원 중복 방지 |
| 저장 경계 | 측정 대기 | 측정 대기 | 측정 대기 | pending·verify·동일 version read-back |

일반 턴의 중앙값, 95백분위, 20초 이내 비율과 규칙 누락/상태 오류를 함께 비교한다. 단순히 빨라졌다는 느낌만으로 검증 완료라고 기록하지 않는다.

## 여전히 느릴 때

검색이 병목이면 다음 개발 단계로 `규칙 ID 여러 개 → 현재 판의 정확한 본문`을 한 호출에서 반환하는 조회 도구를 검토한다. 상태 직렬화/저장이 병목이면 Supabase 앞의 서버가 정형 상태·난수·판정·Checkpoint 검증을 맡고 AI가 관련 상태만 읽는 구조를 검토한다. 현재 저장소에는 이 서버가 구현되어 있지 않다.

모델 자체가 병목이면 사용 가능한 더 빠른 모델이나 응답 설정으로 같은 사례를 비교하되 규칙 누락도 함께 확인한다. 큰 모델을 유지한 채 문구만 바꿔 지연을 일정하게 만드는 데에는 한계가 있다. 실제 로그에서 병목을 확인한 뒤 다음 변경 범위를 정한다.
